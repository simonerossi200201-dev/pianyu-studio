## 现状：地基已经打好了，就差不让它开第二个

`locks.py` 的文件头写得很清楚，它本来就是为"用户同时开好几个 Orante 窗口"设计的：
`account_locks` / `account_waiters` 两张表在共用的 SQLite 里，持有者 20 秒一次心跳，
90 秒不动就判定死亡可以接管，排队按 `(prio, seq)` 决定，**一个账号同一时刻只有一个 Job 在跑**。

数据库也已经是 WAL + `timeout=30` + `check_same_thread=False`。
命令行**已经支持** `python -m orante --port 9401`。

**唯一挡着的是 `main.py` 第 866 行**：发现端口上已经有一个 Orante，就打印
「Orante 已经在运行，已为你打开现有窗口」然后 `return 0`，根本不起第二个。

所以本规格 80% 是"把门打开 + 把冲突显式化"，不是重做架构。

## A. 怎么开出第二个

### A1. 端口自己找

新增 `main.py::pick_port(prefer)`：

- 有 `--port` → 就用它；被占且占的是 Orante → **明确报错退出**（用户指定了端口就别自作主张换）。
- 没指定 → 从 `config.get("ui.port")`（默认 9400）开始，依次试 9400、9401 … 最多 **9420**：
  第一个 `classify_port` 返回"空"的就用它。
- 20 个都满 → 弹现有的 `show_boot_error_window`，文案：`已经开了 20 个 Orante 窗口，先关掉几个`。

### A2. 双击快捷方式 / bat 的行为

用户要的是"不管从快捷方式还是界面内都能多开"。但**误触双开**也很烦人，所以分两种：

- **单击桌面图标 / 双击 `Orante2.bat`** → 默认行为保持"**聚焦已有窗口**"（现在这样，别改）。
  这是大多数时候想要的。
- **按住 <kbd>Shift</kbd> 再双击** → 新开一个。（Windows 上很多软件都是这个约定。）
  `Orante2.bat` 检测 Shift 做不到，所以改成：**`launcher` 那条路上**（快捷方式指向的是
  `.venv\Scripts\pythonw.exe -m orante`）在 `main.py` 里读 `--new`，
  快捷方式那边**再建一个**「Orante（新窗口）」的快捷方式，目标带 `--new`。
- `tools\创建快捷方式.bat` 因此要生成**两个**快捷方式：`Orante.lnk` 和 `Orante（新窗口）.lnk`，
  开始菜单里也是两个。图标相同。

### A3. 界面里开

顶栏（版本号那一带）加一个按钮 `＋ 新窗口`，`title` 写「再开一个 Orante 窗口，可以同时操作不同的任务」。
点了就在后端 `subprocess.Popen` 起一个新进程（`sys.executable -m orante --new`，
`creationflags=DETACHED_PROCESS|CREATE_NEW_PROCESS_GROUP`，不继承句柄），立刻返回，不等它起来。

接口：`POST /api/system/new-window` → `{ok, port}`（端口是新进程自己挑的，所以这里只返回"已启动"，
真实端口让新窗口自己显示）。

## B. 每个窗口要能认出自己是谁

多开之后最容易出的事是**用户分不清哪个窗口在干什么**。

- **窗口标题**：`Orante 制片台 · :9401`，端口跟在后面。第一个窗口（用配置端口那个）不显示端口后缀。
- **顶栏**：版本号旁边显示一个小小的 `:9401` 灰字（第一个窗口不显示）。
- **任务栏分组**：AppUserModelID 保持 `Orante.Studio` 不变，多个窗口归为一组，这是对的。
- 窗口标题里**不要**放任务名——任务是会切的，标题一直变很吵。

## C. 一个账号只能跑一个：把它显式地告诉用户

锁本身已经在做这件事了。问题是现在**看不出来**：另一个窗口占着账号时，这边只会一直"排队中"，
用户会以为卡死了。

### C1. 占用信息要带上"是谁占的"

`account_locks` 表加两列（`db.py` 里照现有 migration 写法加，**旧库要能自动升级**）：

    owner_port   INTEGER   -- 持有者那个 Orante 的端口
    owner_pid    INTEGER   -- 持有者进程号

`AccountLock` 拿锁时写进去。`locks.holder(account_id)` 把它们带出来。

### C2. 界面上说人话

- **账号抽屉**：被别的窗口占着的账号，状态显示 `● 被 :9401 窗口占用中`，橙色。
  自己这个窗口占着的显示 `● 生成中`（绿色，现有行为）。
- **<span>④</span>生成 面板**：某任务的账号被别的窗口占着 → 那一行显示
  `等待中 · 账号被 :9401 窗口占用（排第 2）`，**把排队位置也写出来**（`queue_view()` 现成的）。
- **点开始生成时**：如果这个任务的账号此刻被别的窗口占着，**不要拦**，正常入队（那正是锁的用途），
  但 toast 一句：`账号被另一个窗口（:9401）占用，已排队，轮到就自动开始`。
- **账号下拉里**（66 号那个扩图账号）：被占用的账号后面加 `· :9401 占用中`，**不禁用**（排队是合法的）。

### C3. 三条硬规矩，写进测试

1. 两个进程同时对同一个账号起 Job → **只有一个真正在跑**，另一个在 `account_waiters` 里排队。
2. 持有者进程被强杀（不是正常退出）→ 心跳停了，**90 秒后**另一个窗口能接管，不会永久占住。
3. 不同账号的 Job 在两个进程里**真并行**，互不等待。

## D. 共用一个数据库，别互相踩

### D1. 写冲突

WAL + `timeout=30` 已经挡住了大部分。再加两条：

- `db.conn()` 里补 `PRAGMA busy_timeout=30000`（和 `timeout=30` 双保险，某些驱动路径只认 PRAGMA）
  和 `PRAGMA synchronous=NORMAL`（WAL 下够用，写快很多）。
- 写操作包一层重试：`database is locked` → 退避重试 3 次（80/240/600 ms），仍失败才抛。
  只包**写**，读不包。

### D2. 设置和套装的跨窗口一致性

这是多开 + 76 号套装叠在一起才会出现的坑：**A 窗口切了套装，B 窗口还显示旧的提示词**。

- `settings` 表加一个 `_rev` 行（整数，任何 `config.set` / 套装切换都 +1）。
- 各窗口现有的轮询里带上 `rev`；发现变了 → 顶栏浮出一条：
  `另一个窗口改了配置（切到了「温暖布道」）` + <span class="btn-ref">刷新</span> 按钮。
  **不要自动刷新**——用户可能正在这个窗口里打字。
- **套装切换在有别的窗口正在生成时，同样要拦**（76 号 D 节那条检查，范围从"本进程"扩到"所有进程"：
  查 `account_locks` 有没有活着的持有者）。

### D3. 同一个任务被两个窗口同时操作

- `manifest.json` 的写入已经有锁（`_io_lock`），但那是**进程内**的。多开时两个进程可能同时写同一个
  manifest。加一个**文件锁**：写 manifest 前拿 `<任务目录>/.manifest.lock`（`msvcrt.locking` 或者
  原子创建 + 心跳，选一个，报告里说明），拿不到就等，超过 10 秒报错。
- <span>①</span>任务 面板同一行在两个窗口被同时编辑 → 保存时比对 `updated` 时间戳，
  对不上就提示「这一行在另一个窗口被改过」并给出"用我的 / 用它的"两个选择。**不要静默覆盖。**

## E. 不能多开的东西

有些资源天生独占，多开时必须只有一个窗口在做：

| 东西 | 怎么办 |
|---|---|
| 某个账号的 Chrome / CDP 端口 | 已经被账号锁覆盖，不用额外做 |
| 自动归档（启动时跑的那个） | 只有**第一个**启动的窗口跑。用一个 `settings` 里的 `archive.last_run` + 5 分钟窗口去重 |
| 跨任务描述语队列（<span>②</span>的那个） | 表里记 `owner_port`；别的窗口打开时显示"队列正在 :9400 窗口运行"，本窗口的开关禁用 |
| 尾帧检查台 / 收片的文件写入 | 走 D3 的文件锁 |

## F. 测试

### `tools/test_spec77.py`（**先设 ORANTE_DATA**）

- `pick_port`：9400 被占（假 `classify_port`）→ 返回 9401；9400~9419 全占 → 抛错，文案含「20 个」。
- `--port 9401` 且 9401 上已有 Orante → **报错退出**，不静默换端口。
- **两个"进程"抢同一个账号**（用两个独立的 `AccountLock` 实例 + 不同 token 模拟）：
  只有一个拿到，另一个进 `account_waiters`；`holder()` 返回的 `owner_port` 是占住那个的。
- 持有者停止心跳，把 `heartbeat` 手动往前拨 100 秒 → 另一个能接管。
- 不同账号的两把锁互不阻塞（都能立刻拿到）。
- `db` 写重试：打桩让前两次抛 `database is locked` → 第三次成功，不抛给调用方；
  三次全失败 → 抛出去。
- `_rev`：`config.set` 之后 `_rev` 增加；套装切换之后也增加。
- manifest 文件锁：同一个任务目录，第二个写入者在第一个持锁期间拿不到，10 秒后超时报错。
- 任务行保存时 `updated` 对不上 → 返回冲突标志，**没有写入**。
- 自动归档去重：5 分钟内第二次调用直接跳过。

### 真机验收（报告里贴实况）

这些没法用单测覆盖，**必须在真机上做一遍并把结果写进报告**：

1. 开两个窗口，各选一个**不同**账号的任务，同时点开始生成 → **两边真的同时在跑**。

   `等待中 · 账号被 :94xx 窗口占用`，第一个跑完之后第二个自动接上。
3. 在跑的那个窗口用任务管理器**强杀**掉 → 另一个窗口 90 秒内接管那个账号继续跑。

5. 两个窗口同时打开同一个任务的 <span>⑤</span>收片，各自重生不同的段 → manifest 没被写坏，
   两边的改动都在。
