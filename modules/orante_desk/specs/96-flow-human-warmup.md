# 规格 96 · Flow 人操作式提交（原「冷启动暖场」，2026-09-27 起改为每段常态）

日期：2026-09-27。用户反馈：Flow1（Stefano 账号，刚买的 ULTRA，从没用过）提交第一段就被 Google 判
`PUBLIC_ERROR_UNUSUAL_ACTIVITY` 拒了；但用户在 Flow 网页里手动点击、完全能正常生成。用户明确要求：
「把限流那部分代码删掉」「查一下是不是 Flow 界面/信号变了」「必要的话可以抓信号」，
并在确认手动能生成之后进一步要求：让 Orante 生成的时候完全按照正常人的操作方式来。

## 排查过程

1. **限流不是 Orante 编出来的**：`data/logs/J00658.log`、`J00659.log` 里 `PUBLIC_ERROR_UNUSUAL_ACTIVITY`
   是 Google 那次 `eb1hJf` 请求的原始回包，图片本身传得上去（`maseQ` 成功）、余额也查得到
   （`nzlxg` 正常）。Orante 自己的 20 分钟冷却是收到这个回绝之后**才**加的退避，是果不是因；
   删掉退避代码并不会让 Google 别拒，只会让 Orante 不停头地重复交同一个会被拒的请求。
2. **不是接口/签名过期**：`bl`（构建号）、`at`（XSRF）、`f.sid`、reCAPTCHA token 全部是
   `window.WIZ_global_data` + 页面自己的 `grecaptcha.enterprise.execute` **现场活取**，
   没有一处写死会过期的值；跟 9/22 抓包（`flow_capture_0922-012853.jsonl`）逐字段核对，
   `eb1hJf` 的请求结构（模型 id、静音位、token 位置）完全一致，说明 Flow 没有换协议把 Orante 卡住。
3. **不是账号资格问题**：Flow1 = Stefano 这一个账号（"旭阳""杨伟"是同账号下的项目文件夹，不是
   不同账号），实测模型下拉框最下面确实有「Veo 3.1 - Lite [Lower Priority]」且当前就选中，
   ULTRA 套餐，排除"账号没有无限模型资格"。
4. **真正的差异：有没有人操作的痕迹**。Flow 网页手动生成走的是真实 DOM：点上传框→原生文件选择器→
   打字→点「Start generation」（`type="submit"` 的真按钮）。Orante 原来的路径完全不碰这些——
   直接在页面里 `page.evaluate` 现拼 `f.req` 发 `fetch`，从打开标签页到发第一个生成请求
   往往只有十几秒，中间没有任何鼠标移动、点击、打字事件。reCAPTCHA Enterprise 认的恰恰是这些
   行为信号；一个空标签页第一次就发一个"凭空冒出来"的请求，分数天生就低。而账号一旦"热"过
   （这个标签页已经有过一次真提交），后续同一批段纯走接口直连完全没事——用户自己机器上
   9/21 之后一口气交 40/35 段就是证据，说明并不是"每一发都要装成人"，只是"这个标签页需要
   先有一次真的交互"。

## 修法（原始版本，已被下面的「2026-09-27 三修：每段都走人操作」取代）

`orante/engines/flow_api.py`：

- `FlowEngine.__init__` 新增 `self._ui_warmed`（这个标签页有没有真人操作式提交成功过一次）、
  `self._ui_warmup_failed`（暖场是不是已经试过一次、失败了，不用再白试）。
- `submit()`：算完画幅之后，`_ui_warmed` 和 `_ui_warmup_failed` 都是 False、且
  `flow.human_warmup`（新配置，默认开）没关掉时，先调 `_submit_via_ui(...)`：
  - 真点「Settings trigger」→ 切 Video/Frames → 选画幅/模型/时长 → 关设置；
  - 真点「Start」（起帧格）→ 真点「Upload media」→ `page.expect_file_chooser()` 接住原生
    文件选择器 → `set_files()`；有尾帧（接龙/接片）就照样点「End」再来一遍；
  - 真点提示词输入框（`placeholder="What do you want to create?"`），全选删除后
    `page.keyboard.type()` 一个字一个字打，字符间随机 20–65ms；
  - 真点「Start generation」，用 `page.expect_response()` 被动收那条 `eb1hJf` 响应
    （不是自己拼请求，是等 Flow 自己的前端代码发出去的那条），`_parse_batchexecute()`
    按原来 `RPC_JS` 同一套规则解析出 payload/err。
  - 成功：`_ui_warmed=True`，返回 gen_id，这个标签页往后的段都不再暖场，直接走原来的
    接口直连（原有代码一字未动，原样保留在 `submit()` 下半段）。
  - 真的被拒（`FlowThrottled`/`BlockedImage`/`CreditHalted`）：原样往外抛，**不**落回接口直连
    重交一次——这是 Flow 给的真答案，不是自动化没走通，回退了也只是白白再挨一次拒。
  - 结构性失败（选择器对不上、弹窗没如期出现等，其他任何异常）：记
    `_ui_warmup_failed=True`，打日志说明，落回原来的接口直连——这一段照样能提交成功，
    只是少了这次暖场，后面的段也不再重试暖场（避免每段都白花几秒钟）。
- 新增 `_parse_batchexecute(text, rpc)`：把真点按钮后 `page.expect_response()` 拿到的原始
  响应体，按 `RPC_JS` 里同一套 `)]}'\n\n<len>\n[[...]]` 规则解析成
  `{payload, err, raw}`，跟原来走 `page.evaluate` 拿到的结构对齐，`classify_flow_error` /
  `_g()` 都能直接复用。
- 配置新增 `flow.human_warmup`（默认 `True`），设置 → 生成方式（引擎）新增对应开关，
  关掉就完全跳过暖场、从第一段起就走原来的接口直连（给「这个环境反而更信任接口直连」的
  少数情况留一个退路）。

这套设计当时的想法是**只加保险，不拆原有路径**：暖场失败对任何一段都不是硬性关卡，最坏
情况是"这次没暖成、照旧走原来测试过的接口直连"；但实际两次真机验证（见下面两条补丁）都
在这条"暖场"路上翻车，用户也当场明确表态不想留着接口直连这条"已知会被判异常"的路，
所以设计本身在下面的三修里被替换掉了——保留在这里只是留个档。

## 补丁：Flow2 实测暖场没走通 → 界面语言不是英文

2026-09-27 用户在 **Flow2**（另一个账号，跟 Flow1/Stefano 不是同一个）上真机跑了一次，
日志显示暖场第一步就超时：

```
Locator.click: Timeout 30000ms exceeded ... waiting for get_by_role("button", name="Settings trigger")
```

安全网按设计生效——`_ui_warmup_failed=True`，落回原来测试过的接口直连，图片正常传上去，
只是这一段本来就是冷账号第一发，接口直连照样被 Google 判了 `PUBLIC_ERROR_UNUSUAL_ACTIVITY`。
排查：`Settings trigger`/`Start generation` 这些是**英文**无障碍名称，选择器对不上，最大嫌疑
是这几个专属自动化账号的 Flow 页面渲染成了别的语言。历史抓包文件里 `eb1hJf` 等 RPC 的请求
URL 上能看到 `&hl=it&`（Luca 人在罗马），而 Flow 前端读的 `window.WIZ_global_data.hl` 又是
跟着页面地址栏的 `hl` 查询参数走、并不是账号设置——现场用 Claude in Chrome 验证：拿一个平时
显示英文的账号，手动在项目地址后面加 `?hl=it`，整页立刻变成意大利文（"Inizio"/"Fine" 替换
"Start"/"End"，"Che cosa vuoi creare?" 替换提示词输入框占位文字等），说明 `hl` 这个 URL 参数
独立于账号真实的语言设置，只管这一次页面渲染出来的文字。

**修法**：`orante/engines/flow_api.py`

- 新增 `force_hl(url, hl="en")`：给链接强制加/换 `hl=<hl>` 查询参数，保留其它参数和 fragment，
  空链接原样返回。
- `diagnose_project_page(...)` 新增可选参数 `hl`：非空时，函数内部每一次 `pg.goto(...)`
  （项目链接、去掉合集的备用链接、Flow 首页兜底）都先经过 `force_hl` 处理；不传（保持
  `None`）就完全不改链接，行为跟以前一模一样。
- `FlowEngine._open_own_page()` 调用 `diagnose_project_page(..., hl="en")`——Orante 自己
  专属的这个标签页（暖场点按钮、接口直连都用它）永远强制用英文渲染，这样暖场用的英文
  无障碍选择器才能稳定命中。`probe_account_project_page()`（账号健康检查探测页，只看
  落地地址、不点任何按钮）没有改，继续不传 `hl`，保持原样。
- 这个改动**不会**碰账号真实保存的语言设置——`hl` 只影响这一次 `.goto()`
  渲染出来的文字，账号在别处（比如用户自己手动打开 Flow）打开还是原来的语言；也不会改变
  提交内容本身，`_open_own_page()` 之外提取 `project_id`/`collection_id` 用的正则只看路径段
  （`/project/<uuid>(/collection/<uuid>)?`），不看查询串，不受 `?hl=en` 影响。
  唯一的连带影响是：原来接口直连路径里 `RPC_JS` 现场读 `window.WIZ_global_data.hl` 拼进
  `eb1hJf` 等请求 URL 的 `hl=` 值，以前跟着账号真实语言走（比如 `hl=it`），现在这个专属标签页
  渲染成英文后会变成 `hl=en`——这只是请求里“希望收到的错误提示语言”这一个元数据，不影响
  Google 判断要不要通过这次生成请求。

测试：`tools/test_spec96.py` 新增 `force_hl` 的加参/换参/保留其它参数/保留 fragment/空链接
四个用例，`diagnose_project_page(hl="en")` 真的把 `hl=en` 拼进每一次 `pg.goto()` 链接、不传
`hl` 完全不改链接两个用例，以及 `_open_own_page()` 确实带 `hl="en"` 调用
`diagnose_project_page` 的用例。全部通过。

改前备份：`*.bak-0927hlen`。

**仍待真机验证**：这个假设（Italian/其它非英文渲染导致选择器不匹配）已经通过 `?hl=it`
的独立实验证实了 `hl` 参数确实控制渲染语言，但我没能力直接操作 Flow1/Flow2 在真机上的
Chrome 窗口，所以还没能在这两个账号自己的专属标签页里实跑一次、亲眼看到暖场走通。如果这次
还是没走通，请把新的日志（尤其是「人操作式暖场没走通（……）」那一行的完整报错文字）发回来，
再核对是不是还有别的语言或选择器差异。

（后续更新：`hl=en` 这个修法本身生效了——见下面「补丁二」，用户截图能看到地址栏已经带
`?hl=en`、界面也确实是英文了，暖场往前走了一大步，卡在了另一个此前没发现的 UI 步骤上。）

## 补丁二：语言修好之后，卡在「Select a frame image」弹窗没关

`hl=en` 部署上去之后，用户又跑了一次并发来截图：地址栏确实是
`.../collection/...?hl=en`，界面确实是英文，Settings trigger 那关已经过了，图片也传上去了
——但停在一个「Select a frame image」资产库弹窗上不动，右边预览着刚传上去的图、下面一个
「Add to prompt」按钮没被点。紧接着的真机日志也对上了：这次超时换了个控件——

```
Locator.click: Timeout 30000ms exceeded ... waiting for get_by_placeholder("What do you want to create?")
```

**排查**：`_ui_attach_frame` 原来的逻辑是「点起帧格子→点 Upload media→原生文件选择器
`set_files()`→就当这一帧传完了」，漏了一步——`set_files()` 之后 Flow **不会**直接把图放进
格子，还是同一个「Select a frame image」弹窗，只是新传的图被自动选中、右边多了预览和一个
「Add to prompt」按钮，要真点一下这个按钮，弹窗才关、图才真的进了这个格子。原来的代码没点
这一下，弹窗一直挡在页面上，后面找提示词输入框自然找不到、卡满 30 秒超时。

**修法**：`_ui_attach_frame` 在 `set_files()` 之后新增：等「Add to prompt」按钮出现
（`wait_for(state="visible")`）→ 点一下 → 再等「Select a frame image」弹窗消失（原来就有
这一步，位置往后挪）。起帧、尾帧（接龙场景）各走一遍这个完整序列，所以尾帧也会多点一次
「Add to prompt」。

测试：`tools/test_spec96.py` 的 `test_submit_via_ui_click_sequence_success` /
`test_submit_via_ui_attaches_end_frame_when_given` 新增断言——起帧点一次「Add to prompt」，
带尾帧的话两个格子各点一次、一共两次。

## 三修：用户明确要求——别留接口直连当「热了以后的快路」，每段都走人操作

补丁一、二都是在修「暖场」这一步本身的 bug，但用户看到两次都在这条路上翻车，直接把问题
挑明了：*"你就不走接口直连不行吗？让它在界面上操作全部？既然明知道接口直连被抓包，那还
留它干什么呢？"*

这话有一半是事实、一半是简化：接口直连不是"一直会被抓"，是"一个从没被真人碰过的标签页
第一次提交才容易被判异常"——账号一旦热过，纯接口直连提交几十段完全没事，9/21 那次是证据。
但用户的判断也没错：这一次次真机验证下来，**靠 Orante 自己的自动化去完成"这一次暖场"这件
事本身，比预想的脆弱得多**——先是语言不对选择器全对不上，修完语言又冒出一个没见过的确认
弹窗——既然"暖场只做一次、剩下都走快路"这个设计的前提（暖场能可靠地一次成功）在真机上还
没能稳定兑现，那就没必要再费心思去区分"这段要暖场"和"这段可以抄近路"，干脆每一段都走人
操作式提交，跟用户手动点击时做的事情完全一样。

**改法**（`orante/engines/flow_api.py` `submit()`）：

- 去掉原来「`_ui_warmed` 或 `_ui_warmup_failed` 已经是 True 就跳过 UI」的判断，只要
  `flow.human_warmup`（配置，默认开）没关，**每一段**都先走 `_submit_via_ui(...)`。
- 保留的兜底逻辑不变：这一段本身结构性失败（选择器对不上等）→ 落回接口直连，这一段照样
  能提交成功；真的被 Flow 拒了（限流/审核/额度）→ 原样往外抛，不落回重交。
- 关键变化：结构性失败**不再让后面的段放弃 UI**——`_ui_warmup_failed` 现在只是打日志、
  记个诊断标志位，不再决定下一段要不要试 UI；下一段照旧先走一遍人操作，不会因为上一段没
  成就"学乖了"永久切回接口直连。这样接口直连彻底降级成"这一段万一真出岔子时的安全网"，
  不再是任何一段的常态路径。
- `flow.human_warmup` 这个配置和设置界面开关都还在，语义从"要不要暖场"改成"要不要每段
  都走人操作提交"，i18n 文案（`zh.json`/`en.json`）同步改了说法；关掉就是老底：从第一段起
  就一直走接口直连（给极少数"这个环境反而更信任接口直连"的情况留退路）。

**代价是速度，不是配额**：每段都要真点真打字，比接口直连慢几秒到十几秒，但不会多消耗一次
生成配额（暖场失败也是先在这一段里落回接口直连再提交，不是先烧一次配额再重试）；用户明确
表达了"宁可满一点也要稳"的取向，这个取舍是对的。

测试：`tools/test_spec96.py` 里原来"暖过一次后面就不再调用 UI"的用例改成
`test_submit_uses_ui_path_for_every_segment`（断言每一段都调用一次 UI、UI 一直成功就永远
不碰接口直连）；原来"暖场失败一次后面段不再重试"的用例改成
`test_submit_falls_back_to_direct_on_structural_ui_failure_every_segment`（断言两段都结构性
失败，两段都各自落回接口直连，且第二段照样先试了一次 UI，不会因为第一段没成就放弃）。

## 四修（定稿）：提示词框根本不是输入框；彻底去掉接口直连兜底

三修上线后 Flow2 又跑了一次，截图里首帧已经挂上（「Add to prompt」那一步修好了），
但提示词没进去，停在 `waiting for get_by_placeholder("What do you want to create?")`。
接口直连兜底又被 Google 拒了一次，冷却从 20 分钟翻成 40 分钟。

**根因**（Claude in Chrome 在 flow.google.com 上实测 DOM）：提示词框是
`<div contenteditable="true" class="ProseMirror">`，**没有 placeholder 属性**，占位字是
CSS 画出来的——`get_by_placeholder` 在这个页面上永远找不到它。旧版
`下载图片/core/flow_batch.py` 早就写对了：`EDITOR_SEL = div[role=textbox][contenteditable] ,
div.ProseMirror[contenteditable]`，`fill_editor` = 点框 → Ctrl+A → Delete → `keyboard.insert_text`
（一次性粘贴），`verify_editor` 读回 innerText 逐字核对。这次按这套流程重写（没照抄代码，
选择器按新站实测）：实测真鼠标点进框再输入，文字能进框、「Start generation」随即从灰变亮。

同一轮实测还确认了：作曲区有内容时右上角出现 `button[aria-label="Clear prompt"]`（×），点它
整个作曲区清空；设置面板里有「Output count」x1–x4（Flow2 截图是 x2，一次出两条、Orante 只认
第一条，另一条白烧额度）；模型按钮文字能读回来（个人账号默认停在 Omni 1.1 Flash——不吃图片）。

**改法**（`orante/engines/flow_api.py`）：

- 每段的完整流程 `_ui_fill_and_generate`：清场（Agent 开着就关；有 × 就点 × 清空；清完还没有
  空的 Start 格子就重开一次项目页）→ 设置面板里 Video / Frames / 画幅 / 模型 / 时长 / **x1** →
  **读回模型核对**（对不上就不交）→ Esc → 挂首帧（尾帧）+「Add to prompt」→ **ProseMirror 框里
  一次性粘贴并读回核对** → 等「Start generation」变亮 → 点它 → 被动收 eb1hJf 回包。

## 十一修（2026-09-28 下午，T0122 头几段被判"首帧对不上"）

现场：T0122 的 p01～p04 是正方形图（1200×1200、4096×4096）。s001、s003、s004 下下来的片子
内容完全正确（抽首帧跟配图并排看，一模一样），但 Flow 把正方形图塞进 16:9、左右补了黑边，
首帧校验把整张图压成 16×16 去比，黑边一搅，距离 105～136，对的片被当错件作废两次后判失败。

根因：接口直连时 Orante 把 `_crop_box` 算出的居中裁切框随请求一起交给 Flow，片子是满画面；
改成网页上传后原图原样交上去，少了这一步。修法：

1. `_ui_frame_copy(img, aspect)`：**只给视频首帧 / 尾帧用**。按 `_crop_box` 同一条规则居中裁成
   精确 16:9 / 9:16，长边超过 `UI_FRAME_MAX = 2560` 顺手缩一下（视频最多 1080p，4096 原图白传
   几兆），存成 JPEG q95，名字 `<原名>-<原图 sha1 前 10 位>-16x9.jpg`（同一张图同一画幅永远同名，
   资产库里按名字认准、不重传）。已经是精确画幅又不大的图原样传。扩图 / 高清修复等图片模式的
   参考图**不裁**。
2. 首帧校验（`verify.after_download`，对配图的那一支）：再拿"居中裁过的那一块"
   （`ahash_image_cropped`）比一次，取近的。换成别的图照样差得远，不会放错片。
3. s002 那次「Add to prompt 点不中」：先看到"选中"，紧接着 Flow 自己把图挂进格子、关了弹窗，
   按钮已经没了，8 秒超时整段作废。现在选中后先等 1.5 秒看它会不会自己挂上；点之前、点不中之后
   都再核对一次，已经挂上就算完成。
4. 点「停止」时浏览器被关，排队的段一个个报 `context closed`，被记成"提交失败"（J00762 把
   s002～s075 全记失败）。现在提交出错时如果任务已被取消，这一段原样留着（待做），任务按取消结束。

测试：`test_spec96.py` 新增正方形裁 16:9、竖图裁 9:16、大图缩到 2560、精确画幅原样传、
参考图不裁、晚一步自动挂上不去点已消失的按钮（旧代码能复现失败）、首帧校验裁块比对（错图仍拦）；

## 十二修（2026-09-28 傍晚，不说话的任务片子带声音）

查 T0122 已收的 66 条：17 条带声音（音量 -8～-15 dB，是真声音）。原因：Flow 网页「Return silent
videos」（请求里 `[uuid, 1]`）的意思是"**声音被审核过滤时，照样把没声音的片子给我**"，不是"出无声
视频"——声音没被过滤的片子照样带声音。（0922 的注释本来就写着这层意思，十修时我理解成了"出无声"。）

修法：不说话的任务（`want_silent`）每条片子下载落盘后、做校验之前，`verify.strip_audio()` 把音轨
去掉（`-map 0:v -c copy -an`，画面不重编码、首帧哈希不变），去完再读回确认没有音轨才替换原文件。
开关照旧打开（它能避免声音被过滤时整条作废）。

另外：`verify_task`（复查）也按"裁过的那一块"比首帧；take 上带 `human_ok: true`（人工看过认定内容对）
的片复查时不再判错件——T0122 s001～s004 带黑边的片就是这么放回来的。

测试：`test_spec52.py` 新增去音轨（画面哈希不变、无声的不动、不留临时文件）、生成流程里去音轨在
校验之前、`human_ok` 复查不判错件。
