## 现场

用户在 ①任务 表格「时长」那一列填了 **15**，到 ③编排 一看每段都是 **6s**。
他做的是**不说话**的 B-roll，就是要长镜头。同时他要开始做**横屏**视频了，而软件现在只出竖屏。

## ⚠ 先把原则说清楚（用户亲口定的，别做反了）

**时长由谁定，取决于这个任务说不说话：**

| 任务 | 时长谁定 | 为什么 |
|---|---|---|
| **有文案**（要念台词） | **还是现在的自动规则**：按字数 / 词数拆段、按字数定档，一个字都不改 | 目的是**停顿自然、语速自然**。强塞一个时长，要么念得飞快，要么念完干站着 |
| **没文案**（不说话，B-roll） | **用户填多少就是多少**（引擎能出的档位里选） | 没有台词要念，时长纯粹是镜头长短，由用户说了算 |

所以：**`duration_pref` 只对没文案的任务生效。** 有文案的任务，拆段逻辑、每段时长、`_duration_flow` /
`_duration_grok` / `_to_segments` 的结果都必须和改之前**逐字节一致**（有测试守着）。
"没文案"怎么判定、没文案的任务怎么准备，见 86 号；本规格只负责"没文案时时长听用户的"这一半，
加上下面 Flow 10→8 的暗坑和画幅。

# 第一部分 · 时长

## 根因：「时长」那一列是个摆设

`tasks.duration_pref` 从表格读进来、存进库、显示在表格上——**然后再没有任何代码读过它**。
全项目 grep `duration_pref`，只出现在 `db.py` 建表、`tasks.py` 读写这几处，
`split.py` 和 `generate.py` 一次都没碰。

对**有文案**的任务，这恰好是对的（时长本来就该按字数走）——**这部分不动**。
问题在于：用户那 13 个任务其实**不说话**，只是描述被塞进了文案那一格（86 号处理），
于是被当成台词按字数定成 6 秒，填的 15 完全没用上。

## 还有一个藏得更深的：Flow 的 10 秒会悄悄变成 8 秒

`flow_api.model_id_for`：

```python
if d == 8 or d not in (4, 6):
    return f"veo_3_1_i2v…"          # 8 秒模型
```

**4、6 之外的任何数（包括 10、15）都会落到 8 秒模型上**，没有任何提示。
设置里还有一个 `split.flow.allow_10s` 开关，打开了会拆出 10 秒段，然后提交时被悄悄当成 8 秒。
（这和有没有文案无关，两种任务都要修。）

## 各引擎真正能出的时长（这张表写进代码，所有 UI 都从它取）

新增 `orante/engines/caps.py`，一处定义：

```python
DURATIONS = {"flow": (4, 6, 8), "grok": (6, 10, 15)}
ASPECTS   = {"flow": ("9:16", "16:9"), "grok": ("follow_image",)}   # 见第二部分 E 节
```

**以后任何地方要列时长选项、要校验时长，都从这里取**，不许再在别处写死 4/6/8 或 6/10/15。
`split.flow.allow_10s` 这个设置项删掉（它承诺了一个做不到的事），迁移时如果库里是 true，日志提一句然后忽略。
（自动规则里各档的**字数上限**——`dur_6s_max_chars`、`max_chars_15s` 等——**保持原样**，它们是语速规则，不是能力表。）

`model_id_for` 收到能力表以外的数 → **抛错**，不再悄悄返回 8 秒模型。

## A. 「时长」那一列：只对不说话的任务生效

| 任务 | 「时长」填了什么 | 结果 |
|---|---|---|
| 有文案 | 任何值（包括空） | **忽略**，走现有自动规则（按字数拆段定档）。不报错、不改动 |
| 没文案 | 空 / `自动` | 用 86 号的 `split.no_copy_duration.<引擎>` 默认值 |
| 没文案 | 一个数字 | **每一段都用这个时长** |

- 84 先于 86 执行，所以本规格在 `split.py` 里**新增一个独立函数**，86 号的无文案准备直接调它：

  ```python
  def no_copy_duration(task, engine) -> int:
      """没文案（不说话）任务的每段时长：duration_pref 有值且合法就用它；
      空 / 自动 → settings split.no_copy_duration.<engine>（86 号加这个设置，这里先按 flow=8 / grok=10 兜底）；
      不在 caps.DURATIONS[engine] 里 → 抛 DurationError('Flow 最长 8 秒…')。"""
  ```

  读 `duration_pref` 的地方**只有这个函数**（外加表格显示）。**`split_task` 有文案的分支一行都不许动。**
- 没文案、填的数不在这个引擎的能力表里 → **不许悄悄改**：
  表格里那一格标红 `Flow 最长 8 秒`，准备时拦下来报人话错误。
- 引擎换了（改了账号）而时长不再合法 → 同样标红（只针对没文案的行）。
- 有文案的行里如果存着一个旧的 `duration_pref`（以前导入的），**原样保留、不清空**——
  哪天用户把文案删了，它就自然生效。

## B. 表格里的「时长」那一格

- **没文案的行**：从文本框改成下拉：`自动（按 N 秒）` + 这一行账号对应引擎能出的档位
  （Flow `4 / 6 / 8`，Grok `6 / 10 / 15`），后面带单位「秒」。
- **有文案的行**：显示灰字 `自动（按语速）`，**不可编辑**；悬停说明：
  「有台词的任务按字数自动拆段定时长，保证语速和停顿自然。想自己定时长，把文案清空（不说话的镜头）。」
- 文案那一格一清空 / 一填上，这一格立刻在两种状态之间切换（前端即时，不用刷新）。
- 粘贴 / 导入进来的值不合法（没文案的行）→ 保留原文、标红，悬停说明合法值。别悄悄吞掉。

## C. ③编排 里单段改时长（例外手段，不改变自动规则）

段表的「时长」列可以点开小下拉（同样只给引擎能出的档位）。这是**用户明确要改某一段时的手动例外**，
不影响任何自动拆段逻辑：

- 这一段 `duration` 立刻改，写回 manifest；`sg["duration_manual"]=True`（以后重新拆段不覆盖它）。
- 有文案的段改了之后**明显念不完**（Grok 字数 > 该档上限，Flow 词数 > 该档上限）→ 这一行标黄
  `这段 230 字，6 秒念不完`；**明显太长**（字数远小于该档下限，会念完干站着）→ 标黄 `这段只有 20 字，15 秒会有长停顿`。
  **只提醒不拦**。
- 改过的段在时长旁边显示一个小 `✎`，右键可 <span class="btn-ref">恢复自动</span>（清掉 `duration_manual`，时长回到自动规则算出的值）。
- 已经收片的段改时长 → 标上"时长已改，片子还是旧的"，和 80 号的"旧图"角标一个样式，点一下可以重做这一段。
  **不自动打回**（80 号的原则）。

## D. 批量设时长（只作用于不说话的任务）

- ①任务：勾选若干行 → <span class="btn-ref">更多</span> → <span class="btn-ref">设置时长…</span> →
  弹一个小框，档位按**这批行里没文案的行的引擎**给：全是 Grok 就给 6/10/15，混了 Flow 和 Grok 就分两行各选各的。
  没勾任何行时这一项就是"全部任务"。
- 对话框里写明：「其中 N 个任务有文案，按语速自动定时长，不受影响」。
  如果勾选的全是有文案的任务 → 这一项置灰，悬停说明原因。
- ③编排 段表多选（Shift 点范围、Ctrl 点加减，和 75 号卡片一致）→ 右键 <span class="btn-ref">设置时长…</span>：
  这是 C 节的批量版，同样是手动例外、同样有念不完提醒。
- 已准备的任务批量改时长：**只改还没收片的段**，已收的不动（同 C）；不重新拆段。
  对话框里写明「已经收片的 N 段保持不变」。

# 第二部分 · 画幅

## ⚠ 原则（用户亲口定的）：视频画幅 = 图片画幅，**绝不为凑画幅裁图**

一句话：**用户给什么比例的图，就出什么比例的片。** 横图出横片，竖图出竖片。
不做"任务画幅"、不做"账号画幅"、不做裁剪位置、不做裁剪预览——**为了凑画幅去裁图这件事本身就不许存在**。
用户现在这批不说话的视频原图全是横的，最怕的就是被裁成竖屏、丢掉大半像素，那片子就废了。

## 现状（就是这个坑）

- Flow：画幅挂在**账号**上（`self.aspect = account.get("aspect") or "9:16"`），提交前 `_crop_box` 把图**居中裁**成这个比例。
  **一张横图 16:9 进来，会被裁成 9:16，只剩原图宽度的三分之一左右**——这正是用户担心的事，现在的代码就在这么干。
  而告诉 Flow 画幅的那个整数在 `_gen_inner` 里写死成 `1`（竖屏），见 E 节。
- Grok：`grok_pipe.py` 第 1359 行注释——**传了参考图 Grok 就按图片比例走**。这正好就是我们要的，
  只需确认我们这边上传前没有任何裁剪 / 缩放改比例的步骤。

## E. 抓包结论（Claude 已经分析完，你照着实现，不用再猜也不用再抓）

录制文件：`data\capture\flow_capture_0921-183725.jsonl`（第 17、36、43 条是 `eb1hJf`）。

| 第几条 | 图片 | 图片尺寸 | 网页选的 | `eb1hJf` 里模型 id 后面那个整数 | crop 字段 | 结果 |
|---|---|---|---|---|---|---|
| 17 | `2658efcc…` | 768×1376（竖） | 9:16 · 8s | **1** | `[null,null,1,1]` | 出片，竖 |
| 36 | `10679b0b…` | 5504×3072（横） | 16:9 · 8s | **2** | `[null,0.003876,1,0.996124]` | 出片，横 |
| 43 | 同上 | 同上 | 16:9 · 6s | **2** | 同上 | 出片，横 |

结论：

1. **画幅就是 `job` 里模型 id 后面那个整数：`1` = 竖屏 9:16，`2` = 横屏 16:9。** Flow 只有这两种（用户截图确认）。
   现在 `_gen_inner` 里把它**写死成 `1`**——所以软件现在永远在出竖屏。
2. **crop 的顺序是 `[上, 左, 下, 右]`，不是 `[x0, y0, x1, y1]`。** 证据：5504×3072 比 16:9 略宽，
   需要左右各裁 0.39%，网页发的是第 2、4 位（左、右）。现在 `_crop_box` 的注释和算法把 x 写在第 1、3 位，
   **上下左右是反的**（以前竖图配竖屏，裁的量几乎为 0，所以一直没暴露）。0 用 `null` 表示，这点现在是对的。
3. Flow 网页自己会把图**微调到精确的 16:9 / 9:16**（上面那张只裁了左右各 0.39%）。我们照网页做：
   方向**永远跟图片一致**，只裁到精确比例所需的那一丁点，**绝不跨方向裁**（竖图不会被裁成横的，反过来也一样）。
4. 竖图配横屏，网页上直接提交失败——我们永远不会这么提交，所以不用处理。
5. 生图 `ogiZ0b` 这次没录到：`gen_images(aspect=)` 维持现有传法，只把传进去的值改成源图的方向。
6. 6 秒模型 id `veo_3_1_i2v_s_lite_6s_low_priority` 和 `model_id_for` 现在的拼法一致，不用改。

`caps.ASPECTS = {"flow": ("9:16", "16:9"), "grok": ("follow_image",)}`，
`caps.FLOW_ASPECT_CODE = {"9:16": 1, "16:9": 2}`。报告里把上面这张表抄一遍即可。

## F. 画幅从图片自动算，按段走

- 新增 `caps.aspect_for_image(path, engine) -> str`：读图片宽高（PIL 只读头，不解码全图），
  横图（w ≥ h）→ `16:9`，竖图 → `9:16`。正方形图按横屏走并在日志里记一句。
- **每一段按它自己那张图算**（同一个任务里横竖图混着也各出各的），生成时现算，不存成任务属性。
  ③编排 段表 / ④生成 队列里每段显示一个小灰字 `横 16:9` / `竖 9:16`（只读，告诉用户会出什么）。
- Flow 提交：`_gen_inner` 里那个写死的 `1` 换成 `caps.FLOW_ASPECT_CODE[aspect_for_image(首帧图)]`；
  `_crop_box(img, aspect)` 重写：输出 `[上, 左, 下, 右]`，目标比例就是 `aspect_for_image` 的结果（**方向永远和图一致**），
  只做"微调到精确比例"那一点，和网页一致。删掉 `self.aspect`，不再读账号。
  有尾帧（接龙）时：尾帧图的方向必须和首帧一致，不一致就在提交前报人话错误「首帧是横图、尾帧是竖图，Flow 不支持」，不提交。
- 图片比例和 16:9 / 9:16 差得多（例如 4:3、1:1，微调要裁掉 > 5%）→ 照网页的做法裁到精确比例（这是 Flow 的硬性要求），
  但在段上标一个灰色小提示 `图是 4:3，Flow 会裁掉上下各 X%`，悬停说明。只提示，不拦。
- Grok：上传**原图原比例**。grep 检查上传路径上所有 resize / crop / thumbnail 调用，凡是改变宽高比的一律去掉
  （只允许等比缩小以满足体积限制）。报告里列出检查过的位置。
- 扩图、提升画质（66）、换图卡片（68）、尾帧接龙的提清（67）——`gen_images(aspect=)` 一律传
  `aspect_for_image(源图)`，**出来的新图和源图同比例**；不再读账号。
- `accounts.aspect` 不再参与任何出片 / 出图决定：账号设置里这一项**移除**（库里的列保留，不读），
  迁移日志提一句。grep 断言：`engines/`、`services/` 里不再有 `account.get("aspect")`，
  也不再出现字面量 `"9:16"`（`caps.py` 除外）。

没有任何"设置画幅"的按钮、列、批量操作——**用户想要横片，给横图就行。**
