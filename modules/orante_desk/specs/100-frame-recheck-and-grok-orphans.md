# 规格 100：首帧结构复核 + Grok 孤儿提交找回（2026-10-06，2.0.0-beta.21）

起因：T0124（Grok，60 段）一轮跑下来大量报错。逐条查过以后有两类根因，都不是 Grok 那边的问题，是 Orante 自己判错了。

## 1. 「首帧对不上」是误判

| 段 | 均值哈希距离 | 画面结构相关（自己的配图） | 最像的别的图 |
|---|---|---|---|
| s009 | 33 | 0.97 | 0.19 |
| s011 | 79 | 1.00 | 0.21 |
| s016 | 42 | 1.00 | 0.20 |
| s033 | 33 | 1.00 | 0.40 |
| s035 | 17 | 1.00 | 0.38 |
| s037 | 51 | 1.00 | 0.19 |

逐帧看过，6 条全是对的片子：Grok 去掉了配图的暗角、提亮了绿幕、画幅差一点（1376×768 → 1280×704）。16×16 均值哈希对这种大面积平坦背景的亮度变化非常敏感，于是距离 17~79，被当成拿错作废；作废后重新取地址又下到同一个文件，再作废，最后判失败。T0122 的 `_错件` 里也有十几条同样的情况（结构相关全是 0.999）。

做法（`verify.struct_recheck`）：均值哈希说「对不上」时，不直接作废，先做一次结构复核：

- 片子第 0 帧和参考图都转灰度，画幅对齐（参考图按片子画幅居中裁；两边都裁到较窄画幅；取高的那个），缩到 33×33，算横竖梯度，去均值单位化后求相关。对亮度、对比度、色调、暗角都不敏感。
- 和自己配图相关 ≥ 0.80，且比最像的别的配图高出 ≥ 0.10 → 收下（`frame_rescued`），日志说明「首帧指纹差得多，但画面结构一致」。
- 别的图跟自己差不多像甚至更像时：只有这两张配图本来就几乎是同一张（配图之间相关 ≥ 0.90）才算对——用户要求「两张图非常相似时保持现状」。
- 都不满足才按原规则作废，并说明「首帧更像 pXX」或「和配图也对不上」。

阈值是拿 1142 条已收片子 + T0124 / T0122 的作废片子量出来的：对的片子自己配图相关 0.87~1.00；同一人不同姿势的别的图最高 0.90。T0124 / T0122 / T0016 / T0040 / T0013 上把每条片子故意配给最像的别的图做反例：只有配图本来就几乎同一张时才放行（T0122 的 p08≈p70 等、T0040 的 p05≈p08），其余全部拦下。

复查（`verify_task`）也走同一条复核，复核过的不会再被挪去错件；检查台的接片卡也不因此标红。

**开跑前找回**（`verify.restore_voided`）：开始生成时先翻 `clips/_错件`、`clips/_弃用`，段还没收片、文件名里的图号就是现在的配图、结构复核通过、跟别的段已收的不是同一个文件 → 挪回来标收片，不再重生。在 T0124 的副本上试过：s009、s011、s016、s033、s035、s037 六条全部找回。

## 2. 「提交失败：这一页已经跳到 post 页」其实是提交成功

T0124 有 11 段报这个错（s006、s013、s020、s023、s026、s027、s029、s034、s036、s039、s059），错误里带的会话 Id 全是新的，说明每一次都真的交上去了，Grok 在出片，额度也花了，但 Orante 把段记成了失败，片子成了孤儿。

原因在 `grok_pipe.click_submit`：点了提交只等 1.5 秒，页面还没跳就记「点了没反应」；下一轮先跑 guard（提交前检查），这时页面刚跳到 post 页 → guard 报「不是能提交的铺页」→ 整段失败。

做法：

- 点过 / 按过之后最多等 6 秒看是不是跳页，不再 1.5 秒就去试下一种点法（也避免交出第二条）。
- 点过以后 guard 报错时，先看是不是已经提交上了，是就当成功，照常抓 postId 和会话。
- 万一还是报了这个错：当场按会话在标签页里找那条 post（`GrokEngine.find_orphan`），找到就按已提交接着等。
- 上一轮已经这样丢掉的段：开跑时先按错误里的会话 Id 在 Grok 的标签页里找，找到就接着等出片，不重交；标签页已经关了才重交。

## 3. 下载时网络断一下

s021「下载失败：ECONNRESET」直接判了失败。现在连接被重置 / 超时这类网络错误最多再下 3 次，片子还在那边，不算失败。

## 4. 整台电脑断网

同一天 12:53 那一轮，网断了（`ERR_INTERNET_DISCONNECTED` / `ERR_NAME_NOT_RESOLVED`），35 段在铺页这一步全部判失败（还没提交，没花额度，但都要重来）。现在遇到这类错误：段放回队首，暂停提交，每 20 秒再试；网回来接着提交；约 10 分钟还没网就停下，段都留着待做。

## 测试

`tools/test_spec100.py` 15 条：结构相似度（色调变化、画幅不同）、Grok 色调变化的片子收下、真拿错照样作废并说明更像哪张、两张几乎一样的配图、复查不再作废、检查台不标红、提交后晚跳页算成功且不会多点一次、还没点就在 post 页照旧报错、会话 Id 解析、标签页里找孤儿、generate 找回孤儿不重交 + ECONNRESET 重下、开跑前从错件找回（只找回对的，图号不符的不碰）、断网时暂停不判失败。

## 5. 事故：重生瞬间失效（beta.21 → beta.22 当天修）

beta.21 的「开跑前从错件找回」把用户点「重生」时挪进 `_弃用` 的旧片也当成误判找了回来：标了重生的段一点重生，旧片立刻被拉回、标记消失、没有重新提交（T0124 的 s043、s046、s049、s052）。

修法（三道闸，任何一道都能单独挡住）：

1. `generate(mark_fresh=True)`（重生）和 `redo=True`（重做）**完全不跑**错件找回。
2. 错件找回**只认校验器自己作废的文件**：文件的 sha 必须在 `seg['voided_sha']` 里；没有这条记录的一律不碰。
3. `regenerate` 挪走旧片时把它的 sha 记进 `seg['user_discarded']`，并从 `voided_sha` 里删掉；以后任何时候都不会被找回。

测试：`test_restore_never_touches_user_regen_discards`、`test_regenerate_really_regenerates_marked_segments`（两段真的重新提交、收新片，旧片留在 _弃用）、`test_generate_skips_restore_for_regen_and_redo`。这三条在 beta.21 的代码上都会失败，在 beta.22 上通过。
