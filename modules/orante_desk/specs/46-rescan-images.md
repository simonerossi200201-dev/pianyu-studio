## 现场（T0015 · 自媒体1-李星辰v01）

用户发现网盘里的图放错任务了，于是**在本地目录里手动改名、重排**。磁盘现在是：

    D:\1_PROJECT\2026-09-11\A\T0015-自媒体1-李星辰v01\images\
      p01.jpeg  p02.jpeg  p03.jpeg  p04.jpeg  p05.jpeg  p06.jpeg  p07.jpeg  p08.jpeg   ← 只有 8 个

而 ② 多模态里显示 **9 张**（p01~p09），p09 是「文件不在」。
更要命的是：**卡片上的 p03 和磁盘上真实的 `p03.jpeg` 是完全两张图。**
点右上角刷新，慢，而且没解决。

## 两个独立的毛病

### (1) 缩略图是浏览器缓存的旧图 —— 这是「两码事」的真身

用户改名重排之后，`images/p03.jpeg` 这个**路径没变，内容变了**。
页面上 `<img src="…/images/p03.jpeg">` 地址一模一样，浏览器直接吃缓存，
**永远显示旧内容**，刷新多少次都没用。

spec 30 在收片面板里要求过给 `src` 加 `?v=<mtime>`，但 **② 多模态和 ③ 编排没做**。

### (2) 图库不按目录重建 —— 这是 9 张 vs 8 张的原因

`manifest.images[]` 是当初从网盘下载时建的。刷新只做了「这个路径上的文件还在不在」，
**没有回头扫目录**。所以：改名的认不出、新增的看不见、删掉的还挂着「文件不在」。

顺带一提，磁盘上 `p02.jpeg` 和 `p05.jpeg` **大小完全一样（3026434 字节）**，
很可能是同一张图复制了两份 —— 重建时要提醒。

## 要做的

### A. 所有图片 / 视频的 src 一律带 mtime（根治缓存）

统一一个小工具 `srcWithV(relPath, mtimeMs)` → `…/images/p03.jpeg?v=1789129739475`，
**② 多模态、③ 编排、⑤ 收片、尾帧检查台、挑锚点网格，全部改走它。**

- 后端凡是吐图片/视频列表的接口（`get_review`、多模态的图列表、编排的配图轨等），
  每条都带上 `mtime`。
- **必须用 mtime，不能用随机数** —— 随机数会让每次刷新都重下几百 MB。
- 缩略图如果有另存的缓存文件，键里也要带 mtime。

### B. 新功能：「按磁盘重建图库」

② 多模态的「主体图」标题右边加一个按钮 **`重扫目录`**。
③ 编排也放一个（那边更需要，配图轨直接依赖编号）。

#### 认亲规则（顺序不能反）

1. 扫 `images/` 下的图片文件，**跳过所有下划线开头的子目录**
   （`_候选` / `_弃用` / `_replaced` / `_不合格`）和 `空镜头/`。
2. 每个文件算 **sha256**（按 路径+大小+mtime 缓存，别每次全算）。
3. 和 `manifest.images[]` 里记的 sha256 比：
   - **内容对得上** → 认定是同一张图，**继承它的 `desc` / `pose` / `role` / `status`**，
     哪怕文件名完全变了。这是这条功能最值钱的地方 —— 描述语不用重写。
   - 旧库里没有这个内容 → **新图**，`desc` 留空等着写。
   - 旧库里有、但磁盘上找不到同内容的 → **已删除**。
4. 认完亲之后，按**文件名自然排序**重新分配 `p01…pNN`
   （`p2` 排在 `p10` 前面，不要用字典序）。

#### 编号变了怎么办（这一步最容易出事）

重排必然让编号变。生成一张「旧编号 → 新编号」的映射表，**同步改写**：

- `manifest.segments[].image`
- `manifest.track.pins` 和 `pools`
- `manifest.segments[].bridge.to_image`（36/37 号的锚点）

**被删掉的图**如果还被某些段引用 → 那些段的 `image` 置空并标记
`配图已删除，去编排重新配`，**绝不静默指向别的图**。

#### 先看后改

点「重扫目录」先弹一个预览，确认才落盘：

    ┌─ 重扫目录 ────────────────────────────────────┐
    │  磁盘 8 个文件 · 图库 9 条                        │
    │                                                │
    │  ✓ 5 张认出来了（改了名，描述语保留）              │
    │      p01.jpeg ← 原 p03    p03.jpeg ← 原 p07  …   │
    │  + 1 张新增：p06.jpeg（还没有描述语）              │
    │  − 1 张已删除：原 p09（s004 用着它，会被清空）      │
    │  ⚠ p02.jpeg 和 p05.jpeg 内容完全相同              │
    │                                                │
    │  编号变化会同步改写 3 个段的配图和 2 个钉          │
    │                   [取消]        [应用]           │
    └───────────────────────────────────────────────┘

应用前**自动备份** `manifest.bak-rescan-<时间>.json`。
已经提交/已收片的段（`submitted` / `collected`）**不许改配图**，
列出来提示「这些段已经出片，配图不动」。

### C.「文件不在」的卡片要能自救

现在只是一行灰字。改成卡片上直接给三个动作：

    文件不在
    [重扫目录]  [从图库挑一张替换]  [删掉这一条]

### D. 刷新提速

`spec 30` 的刷新之所以慢，是因为它把能做的都做了。拆开：

- **浅层刷新（点一下 / F5）**：只 `stat` 文件（存在性 + mtime + 大小），
  拿新的 mtime 重刷 `src`。**不算哈希、不问多模态、不扫目录。** 目标 < 300ms。
- **重扫目录**：显式按钮，才算哈希、才重建图库。
- 顶栏刷新按钮**右键菜单**里加一项「重扫当前任务的目录」，
  和深度刷新并列，方便不切面板也能用。

6. 重扫前的 `manifest.bak-rescan-*.json` 确实生成了，内容是改之前的。
7. 「文件不在」卡片上三个按钮都能用。
8. 浅层刷新耗时 < 300ms（报告里贴实测数字），且**没有任何多模态调用**。
