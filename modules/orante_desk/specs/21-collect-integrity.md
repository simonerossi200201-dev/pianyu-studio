## 2. 根因：三处代码合起来把闸门全打开了

### 2.1 `orante/legacy/grok_pipe.py` · `FIND_VIDEO_JS`

    const m = document.documentElement.innerHTML
                .match(/https?:\/\/[^"'\s\\]+\.mp4[^"'\s\\]*/g);

它对**整页 HTML 做正则**。grok.com 的 imagine post 详情页是 SPA，页面里除了本段的
视频，还带着「最近创作」栏和 Next.js 预取的 JSON——**别的 post 的 mp4 地址就在里面**。
所以这个函数返回的是一串候选，本段那个未必在第一个。

### 2.2 `grok_pipe.py` · `is_own_video()` + `probe()`

    if on_post_page:
        return True          # ← 只要"我在自己的详情页上"，页面上任何 mp4 都算本段的
    ...
    real = [u for u in urls if is_own_video(u, post, on_post_page)]
    if real:
        return S_READY, real[0]      # ← 而且闭着眼睛取第一个

`goto_own_post()` 只要 URL 里含本段 postId 就返回 True，于是 `on_post_page=True`，
于是**校验被整个跳过**，`real[0]` 取到的就是页面 HTML 里排在最前面的那个 mp4——
在并发出片的时候，那往往是**先完成的邻居段**。

### 2.3 `grok_pipe.py` · `download_one()`

    if row.get("视频来源") != "post页" \
            and not url_matches_post(url, row.get("postId")):
        raise ...

`视频来源 == "post页"` 就**免检放行**。上一步已经把来源标成了 post页，
所以最后一道闸门也不设防。三处叠加 = 完全无保护。

### 2.4 为什么偏偏在那几秒出事

看日志：`14:25:57 / 14:25:58` 一秒内三段同时「出片」，`14:27:11 / 14:27:12` 又是三段。
并发（`max_conc`）越高、越多 post 在同一时间完成，页面「最近创作」里可用的邻居 mp4 就越多，
`real[0]` 撞车的概率就越大。T0010/T0011 的 6~8s 短段也中过两次
（`T0011-s017-p10-1788827606.mp4`、`T0011-s028-p10-1788827638.mp4` 就是同一现象的残留），
只是数量少没被注意到。**这是概率性 bug，不是偶发意外，必须从闸门上根治。**

### 2.5 顺带解释「重生也拿错」

`J00122.log` 里 14:49 重生 s004，只提交了一个 post，却下载到了 17 时前 s010 的旧生成物
（12751 KB，首帧 p17，台词 409~452）。说明**页面上的陈旧 mp4 会跨运行残留**，
重生这条路同样必须过闸。

## 3. 要做的：四道闸门（后端，必须全做）

### 闸 1 · 取 URL 时要求唯一且可归属　`grok_pipe.probe()` / `FIND_VIDEO_JS`

1. `FIND_VIDEO_JS` 改成**分级返回**，不要再返回一个混在一起的数组：

       { strong: [...],   // <video> / <source> 的 currentSrc|src，且该 <video> 在
                          //   当前 post 的主容器内（从 document.querySelector('video') 起，
                          //   或最靠近视口中心的那个 <video>）
         weak:   [...] }  // a[href] 和整页 innerHTML 正则扫出来的，一律算弱证据

2. `probe()` 只认 `strong`：
   - `strong` 恰好 **1 个** → `S_READY`。
   - `strong` **0 个** → `S_SUBMITTED`（还在生成），**绝不降级去用 weak**。
   - `strong` **≥2 个** → 返回 `S_SUBMITTED`，并 log
     `⚠ 页面上有 N 个视频，判不出哪个是本段，继续等`。**宁可等，不可错。**
3. 无论走哪条，都把看到的全部候选记进 `seen`，超时时能说清看到了什么。

### 闸 2 · 去掉「在自己页面上就无条件通过」　`is_own_video()`

    if on_post_page:
        return True        # ← 删掉这两行

改成：`on_post_page` 只作为**加分项**，最终仍必须满足下面任一：
- `url_matches_post(url, post)` 为真；**或**
- 该 URL 是闸 1 判出的**唯一 strong 候选**（由 `probe` 显式传标记进来，不要靠猜）。

### 闸 3 · 下载前不许免检　`download_one()`

删掉 `视频来源 == "post页"` 的旁路。放行条件改为：
- `url_matches_post(url, postId)` 为真；**或**
- 调用方明确带了 `unique_strong=True`（闸 1 判出的唯一候选）。

两条都不成立 → 抛异常，**该段判 pending 重取，不算失败、不消耗重生次数**。

### 闸 4 · 落盘自证（最关键的一道，零成本、本次能抓 100%）

新增 `orante/services/verify.py`，在**每次下载成功后立刻**跑，不等用户点体检：

**4a　全任务 sha256 唯一**
计算落盘文件的 sha256，与本任务 `manifest.segments[*].takes[*].sha256` 比对。
撞车 → 判 `E_DUP_ASSET`：把新落盘的这份挪进 `clips/_错件/`，该段 `status` 打回
`submitted`，`gen_id` 保留，排进**重新取 URL 下载**的队列（**不是重生**——
生成物还在 Grok 那边，重生是浪费额度）。log 写
`✗ sNNN 下载到的和 sMMM 是同一个文件，已作废，重新取地址`。

**4b　首帧对配图**
用 ffmpeg 抽第 0 帧，转灰度、缩到 16×16、按均值二值化得 256 bit，与该段
`image` 对应的图做同样处理，算汉明距离 `d`：

| d | 判定 |
|---|---|
| ≤ 10 | 通过 |
| 11~16 | `W_FRAME_SOFT` 黄旗，收片墙上提示「首帧和配图不太像」，不拦 |
| > 16 | `E_WRONG_CLIP` 红旗，**当作拿错处理，走 4a 同一条作废+重取流程** |

实测参考值（不要自己改阈值）：对的 0 / 1 / 2 / 2 / 4 / 6 / 7，错的 23 / 26 / 42 / 50 / 60 / 64。

**4c　同图段位的兜底**
两段配的是同一张图时（本例 p17 用在 s003 和 s010、p03 用在 s001 和 s011），
4b 分不出来 —— 靠 4a 兜底即可，**4a 一定能抓到**，因为拿错必然是同一份字节。
另外再加一条：本任务内任意两段的**首帧哈希距离 < 4 且配图不是同一张** → 黄旗
`W_FRAME_TWIN`，提示人工确认。

**4d　凭证留痕**
`manifest.json` 的每个 take 补齐这些字段，便于事后追责：

    {"file": "...", "gen_id": "...", "at": "...",
     "asset_url": "https://assets.grok.com/...",   // 实际下载的那个地址
     "sha256": "...", "bytes": 12345678,
     "frame_ahash": "……64位十六进制", "frame_dist": 2,
     "verdict": "ok" | "dup" | "wrong_clip" | "soft"}

**4e　Flow 引擎同样要过 4a/4b。** Flow 那边的取片路径不同，但「落盘自证」是引擎无关的，
放在 `verify.py` 里由 `generate.py` 统一在下载后调用。

### 3.5 收片入口自动体检

`review.get_review()` 现在只有用户点「运行体检」才算 md5 重复
（`services/checks.py::issues_for` 里那条「与 X 是同一个视频」其实早就写好了，
只是从来没有自动跑过 —— 这就是 T0013 一路绿灯的原因）。改成：
**打开收片面板、以及每次收片完成时，自动跑一次轻量体检**（sha256 + 首帧，
不做响度、不做时长重扫），把问题旗直接标在卡片上。

## 4. 「查漏补缺」：把 拼接成片 按钮换掉

### 4.1 需求

收片顶栏那个 `review.concat`「拼接成片」按钮改成 **「查漏补缺」**
（i18n key 新增 `review.gapfill`，旧 key 保留不删）。点开是一个抽屉，做三件事：

1. **读缺失文案清单**。每个任务可以关联一份 Cutora 产出的
   `…\clips\_stitched\缺失文案清单.txt`。默认按约定路径自动找：
   `<任务目录>\clips\_stitched\缺失文案清单.txt`；找不到就给一个「选文件…」按钮，
   选过的路径记进 `manifest.gapfill.report_path`。
   注意：Cutora 可能把多个任务写进同一份清单（本例 T010/T011/T013 在一起），
   **按 `【组 T0xx】` 分组，只取本任务那一组**。
2. **把缺失区间映射回段号**。清单里给的是「文案第 A~B 词」。用
   `manifest.copy.text.split()` 建立词序索引，每段的词区间 = 前面所有段词数之和。
   缺失区间与哪些段的区间相交，就把那些段标成「文案缺失」。本例应当得到：
   缺 134~173 → s004；缺 197~199 → s005；缺 307~408 → s008、s009；缺 454~465 → s011。
   （注意 ASR 的词序和原文词序会有 ±2 词的漂移，**相交判定要留 3 词的容差**，
   并且只要相交就算，不要求包含。）
3. **一键重生**。抽屉里列出受影响的段，默认全选，底部一个「重生选中的 N 段」，
   直接复用现有 `regenerate` 的入口和参数，不要新写一套。

### 4.2 抽屉长什么样

    ┌ 查漏补缺 ───────────────────────────────────────┐
    │ 清单：…\_stitched\缺失文案清单.txt   [重新读取] [选文件…] │
    │ 组 T013 · 现有 11 段 · 4 处缺失                          │
    ├──────────────────────────────────────────────┤
    │ ☑ s004  第134~173词   The judge signs the papers— …      │
    │ ☑ s005  第197~199词   (John 8:34–35)                     │
    │ ☑ s008  第307~356词   It comes from the Spirit of truth…  │
    │ ☑ s009  第357~408词   And He will not ask: What church…   │
    │ ☑ s011  第454~465词   and how to be set free from sin. …  │
    ├──────────────────────────────────────────────┤
    │           [ 重生选中的 5 段 ]                            │
    └──────────────────────────────────────────────┘

每一行左边给一个小色块（用 `pcolor(seg.image)`，和收片墙一致），点行号能跳到墙上那一段。

### 4.3 不要做的事

- **不要引入 Whisper / 任何 ASR。** 体积会翻几倍，而且和 Cutora 功能重复。
  文案完整性由 Cutora 出清单、Orante 读清单来闭环；
  「拿错片」由第 3 节的四道闸门在**下载那一刻**就挡住，根本轮不到 ASR。
- 不要在这里做拼接。拼接仍然在 Cutora 里做。
