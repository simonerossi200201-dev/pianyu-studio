## 2. 本次事故真正的教训（比 g10 本身重要）

**一个在单进程里顺序跑多个 case 的 golden harness，可以"自洽地错"。**

`--all --repeat 3` 连续多天全绿 —— 因为每次都以同样的顺序、同样的污染跑。
重复三次只能证明**确定性**，不能证明**正确性**。顺序固定时，污染也是确定性的。

所以本任务书的第一优先级不是重录 g10，是**让这类污染不可能再发生、并且可被检出**。

## 3. 切片

### 3.1 切片 1 —— harness 隔离（先做，不要跳过）

**1a. `check_case` 增加字体缓存清理**

`clear_roi_cache()` 旁边加一个等价的字体缓存清理（在 `FontManager` 上加
`clear_cache()` 或等价出口，清 `_font_cache`）。用同样的 try/except 包裹。

目的：任何 case 都不能把字体状态带给下一个 case。

**1b. 录制脚本改为一个 case 一个进程**

`tools/t04f6b2_record_g08_g10.py` 以及今后任何录制脚本：
**每个 case 一个独立进程**（或至少每个 case 一次 `boot_host()`）。
顺序共享 host 的录制方式作废。

如果这个脚本以后不再用，直接删掉，并在 `tests/golden/README.md` 里写明
「录制必须一个 case 一个进程」。

**1c. 新增跨 case 污染检出：`--isolate` 对照**

给 `golden_check.py` 加一个模式（名字你定，`--isolate` / `--cross-check` 均可）：
**对每个 case，分别测「单独跑」和「在 `--all` 顺序里跑」，断言两者哈希相同。**

这是这次事故唯一真正的安全网。`--repeat 3` 检不出顺序污染，这个能。

**1d. 全量审计 —— 这是切片 1 的交付物**

装好 1a–1c 后，对 **g01–g10 全部 10 个 case** 跑 `--isolate` 对照，报一张表：

| case | 单独跑 | --all 里跑 | 一致 | 与当前 expected 一致 |
|---|---|---|---|---|

**判定规则（严格执行）**

- 只有 g10 与 expected 不一致，其余全部一致且单独/顺序同值 → 通过，进切片 2。
- **任何其它 case 出现不一致 → 立刻停，报给我，不要录任何东西。**
  那意味着还有别的污染源，2026-09-13 那次 g01–g07/g09 重录也要重新审。

> 预期：g01–g07/g09 不走 v2 `_qfont`，唯一已知的字体变异点是 v2 专有的，
> 所以它们应当不受影响。但这是**预期，不是保证** —— 用 1d 的数据说话。
