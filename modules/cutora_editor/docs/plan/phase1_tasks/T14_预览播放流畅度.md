## 1. 已确认的根因（Claude 直接读代码得出，Grok 不必重新推断）

`cutora/ui/canvas.py::VideoCanvas.paintEvent`（598 行）→ `_draw_preview_local` → **`FrameRenderer.draw_layers(painter, project, tw, th, self._current_time, ...)`（732 行）**。

也就是说：**每一次重绘，都把整个字幕/覆层合成在 UI 线程上、按工程分辨率（1080×1920）从头做一遍**——文本排版、逐词高亮、描边、阴影、背景框、动画、混合模式，全都重算重绘，然后再由 painter 缩放到画布大小显示。

这解释了你观察到的现象：**没有字幕时不卡，一加字幕就卡**。没字幕时 `draw_layers` 几乎无事可做；有字幕后，一句显示 3 秒的字幕在 30 fps 下要被重新排版、重新光栅化 **90 次**，而它的外观其实只变化几次（逐词高亮才变）。

已经做对、**不要动**的两件事：
- 视频帧解码已经是异步环形队列（`AsyncVideoDecoder`，`canvas.py:877` 附近），不在 UI 线程解码；
- 预览音频已经是"先把带效果的音轨渲成代理再播"（`PreviewFxWorker`），与导出滤镜链逐字一致。

所以瓶颈只有一个：**字幕/覆层层每帧重排重绘。** 专业剪辑软件的做法是：文字只光栅化一次成位图（纹理），之后每帧只做位移/缩放/透明度这类廉价变换，并且合成在 GPU 上。我们用 Qt，做不到全 GPU，但"只光栅化一次"这条完全能做，而且是收益最大的一条。

## 1.5 为什么**不**做磁盘渲染缓存（有实测依据，别走这条路）

有人会想到达芬奇的缓存机制——"Resolve 流畅是因为它把结果预渲染到磁盘了"。**在 Luca 这台机器上，这个解释被他自己的数据否掉了：**

- `D:\Resolve Project Backups` 共 18 个 `Timeline.<时间戳>` 文件，**合计约 1 MB**——那是工程自动备份（防崩溃用），与播放性能毫无关系。
- `D:\CacheClip`（Resolve 真正的缓存目录）共 1,097 个文件、**合计 60 MB，其中 1,094 个是 `.pfl` 音频波峰文件**，视频渲染缓存**一个都没有**。

也就是说：**他的达芬奇在没有任何视频渲染缓存的情况下，套着字幕依然流畅播放。** Resolve 的 Smart Cache / 优化媒体 / 代理媒体默认都是关的，他从没开过。所以流畅不来自缓存，来自它**每帧的活本来就便宜**——文字光栅化成纹理后由 GPU 合成，时间线预览还默认降分辨率。

结论：**本任务不引入任何磁盘渲染缓存。** 磁盘缓存的代价是空间、后台渲染排队、编辑后失效重算、以及"改一下要等一会儿"的体验，用来解决"一句字幕被重复光栅化 90 次"是杀鸡用牛刀。等 Phase 2 有了关键帧、重效果和 4K 素材，再评估代理媒体（已在 P2-10）与渲染缓存。

**但有一样要抄**：那 1,094 个 `.pfl` 就是每个音频文件算一次、之后永久复用的波峰数据——而且他的整个配乐库都有，说明 Resolve 是在**素材入库时后台算好**的，不是等你拖进时间线才算。我们的 T05 已经计划把波形缓存到 `USER_DATA\cache\waveforms\<hash>.npy`，方向一致；**T11 资产库要补一条：添加素材目录时后台预算波峰**，这样音频拖进时间线波形立刻就有。这条不在 T14 范围内，记在这里备查。

## 2. 第一步：先量，再改（本任务的第一次提交只做这个）

- 累计统计输出到 `USER_DATA\logs\preview_perf.jsonl`：每 2 秒一行，含 p50 / p95 / 最大值、实际帧率、掉帧数。
- 新增 `tools/preview_bench.py`：离屏起主窗口，加载一个固定工程（用 golden 的 g01 素材 + 一条 30 秒、每秒一句、开启逐词高亮的字幕），模拟播放 30 秒，输出上述统计。**这是改造前后的对拍基准，前后两份都要附进报告。**
- 报告里必须回答：`draw_layers` 占单帧耗时的百分比是多少？其中文本排版、描边阴影、背景框各占多少（再细分一层计时）？

如果实测结果与 §1 的判断不符（比如瓶颈其实在视频帧或在别处），**停下写报告**，不要按 §3 硬做。

## 3. 按顺序做，每条单独提交，每条之后重跑 §2 的基准

### 3.1 字幕/覆层位图缓存（收益最大）
把"一条字幕在某个外观状态下的样子"光栅化一次成 `QImage`，之后每帧只 `drawImage`。
- 缓存键 = （文本内容, 样式指纹, 排版宽度, **外观状态**）。"外观状态"指真正会改变像素的离散量：逐词高亮到第几个词、节奏动画到第几拍、打字机打到第几个字。**连续量不进键**。
- 位移、缩放、旋转、透明度这类连续动画**不重绘**：缓存基准位图，绘制时用 `painter.translate/scale/rotate/setOpacity` 施加。这一条要逐个动画类型核对 `anim_engine`，哪些能拆成"基准位图 + 变换"，哪些必须重绘（例如逐字模糊、闪光扫过），报告里列一张表。
- 缓存容量按内存上限（比如 64 MB）做 LRU，工程切换 / 样式改动 / 主题切换时清空。
- 现有的 `_SE_SUB_CACHE` / `_SE_OV_CACHE` 是导出路径在用的，**不要改它们的语义**；预览缓存新建一份，放 `cutora/ui/preview_cache.py`。

### 3.2 按显示分辨率绘制，而不是按工程分辨率
现在是"按 1080×1920 画完再缩到画布大小"。改成按画布实际像素画。
- 覆层/字幕层的光栅化尺寸 = `min(画布显示尺寸, 工程尺寸)`，并且**播放时长边不超过 1280**（全屏时画布很大，否则全屏反而更卡——这正是你说的全屏也要流畅那一条）。
- 暂停时恢复到工程分辨率全质量渲染（见 3.3）。

### 3.3 播放时降质，暂停时全质
- 播放中：跳过或用廉价近似替代高斯模糊、发光、羽化这类最贵的效果；按 3.2 降分辨率。
- 暂停 / 逐帧 / 拖动播放头停下后 150 ms：恢复全质量、全分辨率渲染。
- 画布右上角显示一个不打扰的小标记（例如 `预览 · 快速`，`fg2` 色），暂停后消失。**用户必须知道自己现在看的是不是最终画质**——这是这条改动唯一的风险，用标记把它消掉。

### 3.4 限帧与丢帧
- 预览重绘上限 = 工程帧率（无则 30 fps）。
- 如果上一帧的 `paintEvent` 超过了帧预算，**丢掉下一次重绘**而不是排队。绝不允许重绘请求堆积（现在 `self._painting` 只是防重入，堆积的请求还是会一个个跑）。
- 播放推进用单调时钟对齐音频位置，不要用"每次画完就画下一帧"。

### 3.5 脏区域（可选，前四条不够再做）
只有字幕变了就只重画字幕所在矩形。**前四条做完如果已经达标，这条不做**，写进报告说明。
