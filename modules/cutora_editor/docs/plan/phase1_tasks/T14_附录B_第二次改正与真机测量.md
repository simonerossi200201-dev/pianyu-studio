## 1. 嫌疑对象（按可能性排序，都带行号，都必须测）

### 嫌疑 1（最大）：移动播放头会重画整个时间线
`cutora/ui/timeline/widget.py:310`
```python
def set_position(self, pos_ms):
    self.position = pos_ms
    self.update()          # ← 整块 widget 重画
```
播放时每 33 ms 调一次。而 `TimelineWidget.paintEvent`（1087 行）要画：标尺、所有轨道、所有片段、**波形**、以及 Subs 轨上的**每一个字幕块（带文字）**。Luca 这条工程有两百多句字幕。

里面有两处特别贵，都在每次重画时从头做：
- **波形是用 Python 循环逐点构造 `QPainterPath`**（`widget.py:449–469`）：`for i in range(n)` 走两遍，`n` 是可见范围内的峰值点数。默认缩放下整条 3 分 47 秒都在视野里，`n` 可能是上万——**每秒做 30 次**。
- **`_normalize_segments()`**（1049 行）在绘制路径里被调用（1248 行），对两百多条字幕每次重新归一化。

这一条同时解释了"加完字幕才卡"：字幕块和 `_normalize_segments` 的开销是跟着字幕数量走的。

**专业软件的做法**：播放头移动**根本不该触发整块重画**。播放头是一条竖线，画在轻量覆层上，或者只 `update(playhead_rect)`。Resolve 播放时时间线其余部分一个像素都不重画。

### 嫌疑 2：`sync_ui` 的杂活现在按 30 Hz 跑
`main_window.py:7854` 起。播放期间每 33 ms 会做一遍：开场视频的 `source()` + `os.path.normpath` 比对与 `setPosition`、`_sync_sfx_preview()`、`_sync_preview_fx()`、`timeline.set_data()` 的时长检查、播放速率同步。单看都不贵，但没人量过合计。

### 嫌疑 3：真实素材的解码跟不上
上一轮基准用的是 golden 的 g01（小、合成、易解码）。Luca 的是 1080×1920 实拍长片，而且 `QMediaPlayer` 还在**同时对同一个文件解码音频**。`AsyncVideoDecoder.get_frame()` 拿不到新帧时会返回上一帧——画面就会停一下再跳。

## 2. 这一次的测量（一次跑完，能把三个嫌疑区分开）

`tools/preview_bench.py` 重做，**真窗口、真工程、真播放**（调 `toggle_play`，不要手动 `repaint`），窗口态与全屏态各 30 秒，`CUTORA_PERF=1` 时才开启。要记录：

| 指标 | 为什么要它 |

| **画布两次实际重绘之间的间隔** p50 / p95 / 最大 | 这才是用户看到的帧率 |

| `AsyncVideoDecoder.get_frame` 的命中 / 落空次数、落空时返回的是不是旧帧 | 打嫌疑 3 |
| 心跳超时次数（一次 tick 的总耗时 > 33 ms 的比例） | 总账 |
