## 1. 代码里的路径（已核对，行号确切）

`cutora/ui/main_window.py:10715`
```python
def on_seek_request(self, pos_ms):
    self._timeline_ms = int(pos_ms)
    ...
    video_ms = self._timeline_to_video_ms(self._timeline_ms)
    self.media_player.setPosition(video_ms)     # ← Qt 里这是【异步】的
    if self._timeline_playing:
        self.media_player.play()
    self.sync_ui()                              # ← 紧接着同步调用
```

`sync_ui`（7854 行）里第一件事就是：
```python
if offset_ms <= 0:
    self._using_media_clock = True
    self._timeline_ms = self.media_player.position()   # ← 用【还没跳过去】的旧位置覆盖掉刚设好的目标
```

**`setPosition` 是异步的，`position()` 在随后的几十到几百毫秒里仍然返回旧值。** 于是紧跟着调用的 `sync_ui` 把 `_timeline_ms` 又拽回了跳转前的位置；再过一两拍播放器真的跳完了，`position()` 又蹦到新位置。时间线时钟因此在"旧位置 ↔ 新位置"之间来回弹。

这个来回弹传到解码器就是灾难。`cutora/render/readers.py:565` `AsyncVideoDecoder.get_frame`：
```python
if msec < first_msec - 100 or msec > first_msec + 1500:
    ...
    self.seek_req = msec
    self.queue.queue.clear()        # 清空整个预读队列
```
时钟每弹一次，就清空一次 30 帧的预读队列并请求一次新的 seek；而 `run()` 里执行的是
```python
self.cap.set(cv2.CAP_PROP_POS_MSEC, seek_target)
```
——**OpenCV 对长 GOP 的 H.264 做 `POS_MSEC` 定位，要先回到上一个关键帧再往前解码**，1080×1920 的实拍片一次可能就是几百毫秒。来回弹几次，画面就"卡住不动"或者"一卡一卡"。

**而从 0 播放时，`position()` 本来就是 0、目标也是 0，不存在不一致，解码器一路顺序读下去——所以流畅。** 现象与代码完全对得上。

## 3. 假设成立后的修法（按顺序，每条单独提交）

### 3.1 跳转期间不要回读播放器位置
- `on_seek_request` 里记下 `self._seek_pending_target = video_ms` 与 `self._seek_pending_since = time.time()`。
- `sync_ui` 中，只要 `_seek_pending_target` 有效，就**不读 `media_player.position()`**，继续用目标位置推进时钟；当 `abs(position() - target) < 100` 或超过 1 秒超时，清掉这个标记，恢复正常跟随。
- `on_seek_request` 末尾**不要再同步调用 `sync_ui()`**；改成只刷新视图（`timeline.set_position` + `video_canvas.set_data`），不碰时钟逻辑。

### 3.2 解码器的 seek 要去抖 + 丢弃过期帧
- `AsyncVideoDecoder` 加一个 `seek_generation` 计数：每次接受新的 seek 请求就 +1，解码线程放进队列的帧带上当时的 generation，`get_frame` 丢掉 generation 过期的帧，**而不是因为时间对不上再触发一次 seek**。
- 同一个解码器在 **150 ms 内只接受一次 seek 请求**，期间的请求只更新目标值、不重复清队列。

### 3.3 小幅前跳不要 seek
目标在当前队列覆盖范围之后、但差距小于 2 秒时，**顺序丢帧追上去**即可，不要走 `cap.set`。（往回跳、或者差距很大时才 seek。）

### 3.4 如果是单次 seek 本身太贵
改用 `_FFmpegFrameReader`（仓库里已有）做预览解码：`ffmpeg -ss <目标> -i ...` 的输入端定位比 OpenCV 的 `POS_MSEC` 快得多，并且行为可预期。这条改动较大，**只有 §2 的日志指向"单次 seek 极慢"时才做**。
