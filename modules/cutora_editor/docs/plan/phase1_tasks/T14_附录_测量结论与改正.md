# T14 附录 — 测量结论：根因不是绘制，是**预览每秒只刷新 5 次**

> 与 `T14_预览播放流畅度.md` 一起看。**本附录推翻任务书 §1 的结论，与任务书冲突以本附录为准。**
> 分支继续用 `task/T14-preview-perf`。

## 0. 先说清楚：任务书 §1 错在哪

我在 §1 写的是"每帧重排重绘整个字幕层 → **所以才会卡**"。前半句成立（`draw_layers` 确实占单帧 67–75%），**后半句是错的**：单帧 p50 只有 2.9 ms、p95 4.9 ms，30 fps 的预算是 33 ms，差着近十倍。Grok 按纪律停下来是对的，那次测量没有白做——**正是"绘制很便宜"这个否定结论，才让我知道要去别处找。**

## 1. 真正的根因（已在代码里定位，一行）

`cutora/ui/main_window.py:1812`：

```python
self.timer = QTimer()
self.timer.setInterval(200)          # ← 200 毫秒
self.timer.timeout.connect(self.sync_ui)
```

而 `sync_ui`（7854 行）是播放期间**唯一**会调用

```python
self.timeline.set_position(pos)                          # → timeline.update()
self.video_canvas.set_data(self.tasks[self.curr_idx], pos / 1000.0)
```

的地方（`self.timer.start()` 在 3994 行，全局只此一处驱动）。

**也就是说：播放时预览画面每秒只更新 5 次。** 不是每一帧慢，是根本没在出帧。管线本身（异步解码环形队列 + 3 ms 的合成）完全够用，只是没人去要新帧。

**旁证**：`sync_ui` 里自己的注释写着「音效预览也跟着这个 **33ms 的心跳**走」——注释说 33 ms，代码是 200 ms。这个心跳曾经是 30 fps，后来被改成 5 fps（多半是为了省 CPU），注释留在原地没动。

**为什么"加了字幕才明显"**：5 fps 播一段说话的人像，画面变化不大，人眼容忍度高；一旦有字幕，尤其是逐词高亮、弹力、入场这些动画，就变成每 200 ms 硬跳一格，一眼就看出来。这与 Luca 描述的现象完全吻合。

## 2. 第一步：先证伪，五分钟（单独一次提交或者干脆先不提交）

把 `setInterval(200)` 改成 `setInterval(33)`，**不做任何别的改动**，在 Luca 的真机上用他自己那条 3 分 47 秒、带完整字幕的工程播一遍。

- 卡顿消失 → 诊断成立，进入 §3 做正经修法。
- 卡顿仍在 → **停下写报告**，把观察到的现象写清楚（是画面跳、还是音画不同步、还是整个界面发木），不要继续往下做。

这一步只是判断题，**不是最终修法**——`sync_ui` 里还塞着开场视频状态机、音效预览、导出淡入淡出、时长检查等一堆杂活，让它们全部按 30 Hz 跑是浪费，也可能引出新问题（比如每 33 ms 就去 `intro_player.setPosition`）。所以必须做 §3。

## 3. 正经修法：把一个心跳拆成两个

### 3.1 快心跳（新增，间隔 = 工程帧率，默认 33 ms）
只做四件廉价的事，别的一律不做：
1. 推进 `_timeline_ms`（时钟逻辑照搬现有的 media clock / 手动累加分支，一个字不改）；
2. `self.timeline.set_position(pos)`；
3. `self.video_canvas.set_data(task, pos/1000)`；
4. 音频淡入淡出的 `setVolume`（这几个调用很便宜，而且 200 ms 一档人耳听得出来）。

**丢帧保护**：记录上一次快心跳的耗时，如果超过间隔就跳过下一次，绝不让重绘请求堆积。

### 3.2 慢心跳（保留现在这个 200 ms 的）
其余全部留在这里：开场视频的 source/seek/播放状态、`_sync_sfx_preview`、`_sync_preview_fx`、`timeline.set_data` 的时长检查、播放速率同步、时间码刷新。

### 3.3 暂停时
快心跳停掉（没有必要空转），慢心跳继续。拖动播放头时按拖动事件直接刷新，不依赖心跳。

### 3.4 把注释改对
`sync_ui` 里那句「跟着这个 33ms 的心跳走」要改成指向新的快心跳，别再留一句和代码对不上的话。

## 4. 第二步：在**真实条件**下重测（这次的基准是错的，要重做）

上一轮的基准有三处与真实情况不符，结论因此不可用：
1. **offscreen** 而不是真窗口；
2. 用的是 golden 的 g01 素材（小、合成、易解码），不是 Luca 的 1080×1920 实拍长片；
3. 只驱动了 `repaint()`，**完全绕开了真正的播放循环**——而根因恰恰就在那个循环里。

新基准 `tools/preview_bench.py` 必须：
- 起**真窗口**（不是 offscreen），加载 **Luca 指定的真实工程**（他会提供一个 3 分 47 秒、带完整字幕的 `.asproj`），走**真正的播放**（`toggle_play`），而不是手动调 repaint；
- 记录：**画布两次实际重绘之间的间隔**（这才是用户看到的帧率）、快心跳耗时、`timeline.paintEvent` 耗时（**上一轮完全没测时间线的绘制，它每次播放头移动都要重画所有轨道、所有字幕块和波形，很可能比画布还贵**）、`draw_layers` 耗时、丢帧数；
- 窗口态与全屏态各跑 30 秒。

## 5. 什么时候才做原任务书 §3 的位图缓存

**只有在快心跳落地、重测之后仍然达不到指标时才做。** 如果 33 ms 的预算里画布 5 ms、时间线若干毫秒、心跳杂活若干毫秒，加起来还很宽裕，那么位图缓存就是过度优化，**这一轮不做**，写进报告说明理由。原任务书 §3.2（按显示分辨率绘制）、§3.3（播放降质）同理——先看数据，别先动手。

**§1.5「不做磁盘渲染缓存」的结论不变**，而且现在理由更强了：连每帧 3 ms 都嫌不够快的地方根本不存在，问题从来不是算得慢。
