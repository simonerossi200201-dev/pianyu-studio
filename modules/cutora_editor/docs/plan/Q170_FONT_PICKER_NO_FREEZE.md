# Q170 · 选字体不卡死（2026-10-06）

Luca：选字体时经常把整个软件卡死（标题栏「未响应」），要求找到根因、彻底优化，用最专业的方式选字体 / 预览字体，
保证怎么选怎么切都流畅、美观。

## 根因调查

用 Luca 的真实工程（HB.json.cutora，路径重映射）在云端逐个切换全部 213 个字体：每次切换约 0.6 秒，**没有复现**
长时间卡死。Luca 的 cutora.log 显示界面线程在 02:50:32 → 03:00:20 之间一行日志都没有（整整 10 分钟），
最后存下来的字体是 **Bitcount Prop Single Ink**（COLRv1 彩色字体 + 11 个可变轴），那段文字还带纸纹背景框、
「God」强调词（放大 1.25 + 描线动画）、按框缩小。

结论分两层：

1. **确定的、所有机器上都有的界面线程开销**（已修）：
   - 字体下拉框每次填充都用 fontTools 把 213 个字体的 cmap 解一遍，判断「缺不缺本语种字符」——冷启动约 4 秒，全在界面线程；
   - 第一次用到某个大 CJK 字体时排版要现解 cmap（几百毫秒）；
   - 原生下拉框滚轮会一格一格切字体，每一格都触发整段文字重新排版 + 重画，鼠标一滚就是十几次重排。
2. **只在某些 Windows 机器上出现的「一卡几分钟」**：最可能是 Windows DirectWrite 渲染彩色 / 多轴可变字体
   （COLRv1）时卡在 C++ 里。云端（Linux / FreeType）无法复现，Python 也打断不了 —— 所以做成「在子进程里先试、
   卡住的字体自动停用」，并加上看门狗，下次再卡能直接看到卡在哪一行。

## 改了什么

| 位置 | 内容 |
|---|---|
| `cutora/subtitle/font_coverage.py` | 拉丁语种覆盖查预先算好的 `font_script_coverage.json`（与解 cmap 结果逐个比对 0 差异）；可变字体按具名实例前缀匹配。下拉框填充 4000 ms → 4 ms。 |
| `cutora/ui/widgets/font_picker.py`（新） | 专业字体选择器：每个字体用自己的字形显示名字、搜索（开头匹配优先）、最近使用、底部大样张（写当前文字）。字形预览全部在后台线程画，界面线程不排版不画字；↑↓/PgUp/PgDn/Enter/Esc，直接打字就是搜索。 |
| `cutora/ui/panels/fonts.py` | 所有字体下拉框点击 / 空格 / F4 / Alt+↓ 打开新选择器；**滚轮不再切字体**；启动 1.5 秒后后台预热全部字体的 cmap。`render_font_family()`：真正拿去画的家族名（会卡死的 → 默认字体，工程数据不改）。 |
| `cutora/core/stall_watchdog.py`（新） | 界面线程卡住 ≥ 0.5 秒就把卡住时的 Python 调用栈写进 cutora.log（`cutora.stall`），一直卡就每 2 秒再采一次。 |
| `cutora/ui/font_probe.py`（新） | **字体体检**：子进程里把每个字体按画布 / 导出同一条路真画一遍（drawText、QPainterPath、完整文本覆层含背景框 / 强调词 / 按框缩小、列表行字号）。超过 12 秒没画完 = 卡死 → 杀掉子进程、停用这个字体、从下一个继续；子进程中途崩了 = 崩溃 → 停用。结果按字体文件 + Qt 版本签名缓存，字体不变不再重测。子进程低优先级，不抢剪辑的 CPU。 |
| 风险字体先挡 | 彩色字体（COLR / CBDT / sbix / SVG）和可变轴 ≥ 4 的字体（现在 9 个，含 Bitcount）排在体检最前面；体检出结果之前先用默认字体显示（第一次启动约 3 秒），查清没问题自动换回原字体并重画。体检本身跑不起来就不挡（不能让字体永远用不了）。 |
| 停用后的表现 | 选择器里这一行灰掉、标「会卡死·已停用」、点了不选；老工程里用到它 → 用默认字体显示 + 状态栏说明一次 + 日志，工程里的字体设置原样保留。慢字体（≥ 1.5 秒）标「较慢」，仍可用。 |
| `cutora/app.py` | 启动时：字体装好后先 `prepare()`（读体检缓存 / 挡风险字体，约 0.1 秒），主窗口出来后装看门狗、预热 cmap、2 秒后开始体检；体检结果变了 → 清文字缓存、重画画布。 |
| 其他 | `combo_popup` 跳过字体下拉框；属性面板把当前文字给选择器做样张；画布行内编辑 / 图层缩略图 / 字幕风格缩略图 / 字体管理对话框改用 `render_font_family`；QSS 加 `#fontPicker` 样式。 |

## 第二轮（10-06 上午，Luca：「工程刚打开、点一下画面就卡死」）

Luca 机器上的日志把根因**坐实**了：

- 字体体检在他电脑上把 **Bitcount Prop Single Ink、Kalnia Glaze、Nabla、Sixtyfour Convergence**（全是 COLRv1 彩色字体）
  一个个判成「渲染超过 12 秒没完成」—— Windows DirectWrite 画这几个字体就是会卡死。体检结束共停用 45 个家族
  （Windows 把可变字体的每个具名实例都登记成一个家族，Bitcount 一个文件就有几十个）。
- 看门狗记到一次「界面线程卡了 240 秒」，栈最内层就是事件循环 = 卡在 Qt 的 C++ 里（画字），不在 Python 代码里。
- 在云端用插桩复现：打开 Luca 的工程 → 点画面上的文字（选中）→ 属性面板的文字框（`text_rich._set_fmt_family`）
  用工程里存的字体 Bitcount 给 QTextEdit 排版 —— **这是第一轮漏掉的路**（第一轮挡住了画布 / 导出 / 选择器，
  没挡编辑框）。以前「选字体就卡死」也是同一条路：换字体 → 文字框按新字体重排。

第二轮修了：

| 位置 | 内容 |
|---|---|
| `panels/text_rich.py` / `panels/text_editors.py` | 编辑框里显示用 `render_font_family`（停用字体换默认字体）；真实家族名存在格式的自定义属性里，读回 / 存盘用它，工程数据不变。插桩复测：打开、单击、双击、切所有标签页、打开字体选择器、文字条，停用字体一次都没进到 Qt。 |
| `ui/font_probe.py` | 一个字体卡死 / 崩溃 → **同一个字体文件的所有家族一起停用**（以前 Bitcount 几十个实例每个等 12 秒 + 重启子进程，要十几分钟）；子进程按「渲染子进程」起，不再加载 torch / CUDA；待测清单走文件；**导出 / 渲染子进程也读体检缓存**，主程序停用的字体导出时同样换默认字体。 |
| `core/stall_watchdog.py` | 真卡死不恢复时也写日志：卡到 3 / 10 / 30 / 60 秒各写一次「此刻卡在哪」，之后每分钟一次；栈最内层是事件循环时注明「卡在 Qt 的 C++ 里」。 |
| `ui/main_window.py` | 打开工程时「素材尺寸 vs 画布」要逐个 ffprobe 素材（日志里每次卡界面 1~1.7 秒）：去重、并行、按（路径, 大小, 修改时间）记住。 |

## 如果还卡

看 `C:\Users\<用户>\AppData\Local\CUTORA\logs\cutora.log` 里的「界面线程卡了 X 秒，卡住时在：」和「字体体检：」两类行。
