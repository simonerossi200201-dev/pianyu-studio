# 每一条任务书都默认附带的规矩（2026-09-19 起）

写在这里，任务书里不再重复。**Grok 开工前必须读这一份。**

## 一、测试的规矩（这一条是这次审计的直接产物）

1. **测试必须用会暴露缺陷的参数，不许用正好绕开的参数。**
   审计发现的六个反例：用单词 `"MMMMMMMM"` 测渐变（测不出按词重置）、
   用 `width_em=0.08` 测描边（测不出 ROI 裁切）、用 `pad_em=0.0` 测进度条、
   用 `distance_em=0.18` 测阴影（测不出 0 距离失效）、只测平行光不测点光、
   断言前先 `reload(force=True)`（正好绕过「自动刷新没发生」这个 bug 本身）。

2. **写完一条测试，先把被测代码故意改坏，确认它会红。不会红的测试不算数。**
   在 `.ok` 里写明你是怎么验证它会红的（改了哪一行、红在哪一条断言）。

3. **下面这些不算测试**，写了也不许写进 `.ok` 当证据：
   - 在源码里 grep 字符串（「源码里必须出现 `xxx`」）
   - 同参数调同一个纯函数两次比结果
   - 断言 `> 0` 而没有阈值
   - 断言某个对象存在、某个按钮被创建
   - 条件写错导致两个分支其实是同一条路（例如 `runs: []` 是假值，
     和「没有 runs」走同一个分支）
   - 只测 helper 不走产品真实调用路径

4. **凡是涉及渲染的改动，必须同时断言预览和导出。**
   这个项目已经在 preview≠export 上翻过四次车（Q13 音频转场、Q17 玻璃描边、
   Q30 代理轨窗口、更早的字幕键路）。断言方式是两边各出一帧比 MAD 或比 md5，
   不是「两边都调了同一个函数」。

## 二、门禁的规矩

5. **不许给测试写文件白名单。** 新写的检查一律扫整个 `cutora/ui/` 或 `cutora/render/`，
   不许只扫自己这次碰过的文件。历史反例：`test_t25_no_hardcoded_px` 硬编码只扫两个文件，
   于是 QSS 里 338 个裸 px 三个月没人管。

6. **分段的绿不等于全局的绿。** 如果你只让自己这一段的像素锁转绿，
   必须在 `.ok` 里写明全局 `test_t18_no_dead_controls` 当前是红是绿、死几个，
   不许用「本段全 live」代替。

## 三、基线红线（不变）

7. golden 十二例、UI 六例，**任何一例哈希变了，立刻写 `docs/plan/queue/_done/Qnn.stop` 并停下**。
   **绝不允许自己重录基线**，不许碰 `tests/**/expected.sha256`，
   不许跑 `tools/_diag/t11g_record_one.py` 或 `RERECORD_GOLDEN.bat`。
   这条权限只属于 Luca。

8. `docs/plan/PROTECTED_INVARIANTS.md` 里的不变量不许碰。

9. 不引入中国服务器 / CCP 关联依赖 —— 一字不改，这是安全问题不是许可问题。
   字体只用已入库的 OFL/Apache。不动 CRF/preset，不加「快速模式」。

## 四、`.ok` 的规矩

10. `.ok` 里必须有：HEAD、新增/修改的测试文件名与测试函数名、
    每条测试「我把哪一行改坏、它红在哪条断言」、golden 与 UI 基线的结果、
    以及**任务书里你没做到的条款**（做不到就写做不到，不许省略）。
    历史反例：Q35 发现 golden `g16` 是红的，只在 `.ok` 里记了一笔，既没解决也没写 `.stop`。

## 五、收尾必须提交（2026-09-19 Q42 之后加）

16. **任务结束前必须 `git commit` 自己的改动。** Q42 做对了活、写了 `.ok`，
    但一行都没提交，改动裸在工作区里。后果有三个：
    - 运行器的隔离机制靠「HEAD 前后对比」定位这一轮的提交，没有提交就**无法归属、无法回滚**；
    - 下一条任务直接盖在上一条未提交的改动上，出问题分不清是谁的；
    - `.ok` 里写的 HEAD 是假的（它指向上一条任务的提交）。

    提交信息第一行写 `Qnn: 一句话说清做了什么`，正文说明改了哪些文件、为什么。
    **只提交自己这一轮的改动**，不要 `git add -A`（仓库里有 `build/` 等不该入库的产物，
    也有其他任务或 Claude 正在写的文件）。

17. **「没做到」的部分要单独列一段，而且要说清楚用户会看到什么现象。**
    Q42 这一点做对了，值得照抄：它写明「`load_data` 走 blockSignals + setValue 只写 spin，
    加载后滑条拇指可停在 0，直到用户去拖」——这就是一句用户能验证的现象描述，
    而不是「部分场景下同步逻辑待完善」这种糊弄话。

## 七、队列自己也会出错（2026-09-20）

运行器在 Q51→Q46→Q52→Q55 之间空转了三圈。原因：守卫隔离一条任务时
`git stash push` 整个脏工作区，而 `tools/grok-queue.txt` 是入库文件，
于是它被还原成上次提交的内容，队列倒带。现在 stash 只收 `cutora/` 和 `tests/`，
并且同一条任务在一轮里出现超过两次就写 `_HALT`。

对你的影响：**如果你发现自己正在做的任务「看起来已经做过了」**（代码已在树上、
`.ok` 已存在），不要闷头重做一遍。先在 `.ok` 里写明「本轮为复验，产品改动已在 <commit>」，
跑一遍验收确认没被后续任务改坏，然后**如实报告这是重复调度**。
Q46/Q51/Q52 各被重复调度了三次，它们都是这么处理的 —— 这个反应是对的。

## 八、每做完一个子项就提交一次（2026-09-21）

昨晚 Q32（调色）和 Q36（竖排）都死在 **xAI 服务端的 `inference idle timeout after 3600s`**
—— 模型挂了一小时没吐任何东西。这不是我们的代码，也不是任务太难，是基础设施不稳。
我们改不了 xAI，**只能让每次挂掉损失最少**。

所以：**任务书里每个编号子项做完、测试绿了，就立刻 `git commit` 一次。**
不要攒到最后一起提交。Q32 写了 704 行 `grade.py` 却没提交，挂掉时全靠运行器兜底；
要是它每做完一块就提交，接手的人一眼就知道做到哪了。

提交信息写 `Qnn(子项编号): 一句话`。
