# Q72 · 批量并行导出时，每个子进程各开 8 个线程互相抢 CPU

**开工前先读 `docs/plan/queue/_RULES_FOR_EVERY_TASK.md`。**

这一条很小，但 **Luca 正是批量用户**——他日常是一次导出一个文件夹的几十条 AI 视频。

## 事实

Q11 让「单视频解码串行、叠字幕并行」，`workers>1` 走 `run_compose_pool`（`render_worker.py:735`）。
单条导出没问题。**但批量并行导出时：**

- `render/parallel.py:278` 建 RenderWorker 时**不传 `compose_workers`**
- 子进程环境（`:650-655`）只设了 OMP 线程数，**没设 `CUTORA_COMPOSE_WORKERS`**

结果：N 个子进程**各自**开 `min(CPU, 8)` 个叠层线程，再各带一个 256MB 的在途缓冲。
4 个并行导出 = 32 个叠层线程抢 CPU + 1GB 在途内存。
而 `plan_parallel_export` 的内存预算**没把这部分算进去**——
这正是 9 月 18 号「黑屏两次」那个问题的同一类风险（内存预算失真）。

## 要做的

1. `parallel.py` 给每个子进程设 `CUTORA_COMPOSE_WORKERS = max(1, cpu_count // n_jobs)`。
2. `export_guard.py` 的内存预算加上每个 worker 的在途缓冲（256MB × n_jobs）。
3. `compose_parallel.py` 里的 `ChunkDispatcher` 是死代码（产品零调用），删掉。
4. `take_next` 固定 30 秒超时，一帧没到就整个导出失败。改成按「解码线程还活着」判断：
   解码线程活着就继续等，死了才失败。

## 验收

- `test_q72_parallel_sets_compose_workers`：模拟 4 个并行任务、16 核，断言每个子进程拿到的
  `CUTORA_COMPOSE_WORKERS == 4`。
- `test_q72_memory_budget_includes_inflight`：`plan_parallel_export` 的预算里有在途缓冲这一项。
- `test_q72_slow_decoder_does_not_timeout`：解码线程故意每帧 sleep 40 秒但还活着，导出不失败。
- **golden 必须逐字节不变**——这是资源调度，不许改输出。`PROTECTED_INVARIANTS.md` 里 export_guard 和 parallel
  的条目要读，不许碰它们保护的逻辑，只许加这两个参数。
