## 要做的

   先 `git stash branch q14-recover stash@{n}` 在独立分支上展开，
   确认能编译、能起窗口，再决定哪些 hunk 值得留。
2. 逐个文件判断：这一处改动是**做完了的**、**做了一半的**、还是**探索留下的垃圾**。
   做了一半的补完，垃圾丢掉。判断依据写进 `.ok`，一个文件一行。
3. 原任务书 `docs/plan/queue/Q14.md` 的验收条款逐条对照，补齐没做的。
4. 特别注意 Q15 留下的两个缺口，一并在这里补掉：
   - `main_window.py:491 IMG_EXT = {.png,.jpg,.jpeg,.webp,.svg}` —— **`.gif` 不在里面**。
     静态单帧 gif 拖进来仍然是什么都不发生、也不报错。
   - `main_window.py:4196 try_import_animated(path)` 和 `assets/user.py:156`
     **都没传 fps** → 序列帧退回硬编码 30。`batch_load.py:259` 和
     `script_insert_image.py:908` 是传了的，这两条漏了。
   - `main_window.py:4195-4214` 动画导入失败会报三遍（statusBar + QMessageBox，
     而 `animated.py:210-220` 自己已经既写状态栏又弹框）——**会弹两个对话框**。收敛成一次。
5. Luca 对这个功能的原话，验收时按这个对：
   > 资产库里应该让用户可以把自己本地资产加载进来而且可以直接挪用到时间线上使用到画面上，
   > 而且**必须要完美的支持带有透明格式的 Gif 文件 和 带有透明格式的达芬奇软件导出的 mov 格式的大文件**。

   「大文件」是关键词 —— 达芬奇导出的 ProRes 4444 带 alpha 的 mov 动辄几个 GB，
   不许整段读进内存。要走流式解码 + 代理，并且测一个真的大文件（可以用 ffmpeg 造一个
   1920×1080、30 秒、带 alpha 的 ProRes 4444，约 1–2 GB）。

## 验收

- `test_q49_gif_alpha_roundtrip`：造一个带透明的多帧 GIF，导入 → 放到时间线 →
  **导出一帧，断言透明区域真的透出了下层画面**（不是黑、不是白）。
- `test_q49_prores4444_alpha`：ffmpeg 造一个带 alpha 的 ProRes 4444 mov，
  同样断言导出帧的透明区透出下层。
- `test_q49_large_file_memory`：导入那个 1–2 GB 的文件，
  断言进程 RSS 峰值增量低于阈值（比如 500 MB）—— 证明没有整段读进内存。
- `test_q49_static_gif_imports`：单帧 gif 拖进来能作为静态图导入，不是静默无反应。
- `test_q49_import_error_reported_once`：导入一个坏文件，断言只弹一个对话框。
- `test_q49_sequence_fps`：序列帧按工程 fps 导入，不是 30。
- golden 与 UI 基线：变了写 `.stop`。
