# Q57 · 重录 golden 的 g19b-2（Luca 2026-09-20 已批准，仅此一例）

## 授权

标准命令是「golden 基线变了停下报 Luca，绝不许自行重录」。**这一条是 Luca 当面批准的例外，
只覆盖 `g19b-2_stitch_crossfade` 这一例。** 他选的是「批准重录，但必须留完整证据」。

## 为什么这条基线是错的

`tests/golden/g19b-2_stitch_crossfade/project.asproj.json` 里**五个片段有四个 `in_t: 0.0`**
—— 它们从源素材第 0 秒开始。而交叉溶解要求后一个片段播它入点**之前**的帧，
`in_t=0.0` 意味着一帧余量都没有。`_get_video_frame_at_time` 在范围外 `return None`，
离屏缓冲 `fill(0)` 全透明，叠到黑画布上就是 Luca 报的「半透明画面半黑」。

**这条基线当初录下来的，就是这个缺陷本身。** Q55 修好它，这条必然变。
新哈希 `got=802a86a1d2c7`（旧 `exp=e0048cebe258`）在两次完全独立的运行里一模一样，是确定性的。

这和 2026-09-19 那次「golden 是用一条在 40% 像素上偏离 H.264 规范的解码器录的」同形：
**基线不是真理，它只是某一天的产物。**

## 顺序：先取证，再重录，最后验证。不许颠倒

### 一、证据（这是这条任务的主要产出，不是附属品）

产物全部放 `docs/plan/reports/Q57_g19b2/`：

1. **逐帧对照图。** 找出每个接缝的转场窗口，在窗口内均匀取 5 帧（含首、中、尾），
   每帧出一张三联图：**修复前 | 修复后 | 差异热力图**。五个接缝都要。
2. **亮度曲线。** 整条片子逐帧算最小亮度和平均 alpha，画成两条曲线（修复前 vs 修复后）。
   修复前应该能在转场窗口看到明显的下陷，修复后不应该有。**这张图是给 Luca 一眼看懂的那张。**
3. **一段可播放的对比视频** `Q57_before_after.mp4`：左右分屏，左边修复前、右边修复后，
   只截转场那几秒，循环两遍。Luca 是做视频的，他要看的是动起来的样子。
4. **数字表**：每个接缝的余量（帧数）、转场时长（帧数）、缺口（帧数）、
   修复前该窗口的最小亮度 / 最小 alpha、修复后的同样两个数。

如果这些证据显示修复后**仍有**发黑（最小亮度接近 0 或 alpha < 255），
**停下写 `.stop`，不要重录** —— 那说明 Q55 还没修干净。

### 二、重录

5. 录制前确认环境指纹和上次录制一致（`fonts_count`、`fonts_digest`、ffmpeg、cv2、numpy、PySide6）。
   **任何一项不一致就停下** —— 这个项目刚吃过「基线是用错的解码器录的」的亏。
6. **只重录 `g19b-2_stitch_crossfade` 这一例。** 其余十一例一律不碰，
   `g16_parallel_fx` 那条老账也不碰（它是另一回事，归 Q47）。
7. 重录之后立刻重跑一次，确认新哈希和重录时的值**逐字节相同**（证明是确定性的，不是录了个随机结果）。

### 三、收尾

8. 写进 `docs/plan/STABLE_POINTS.md`：日期、原因（基线录的是缺陷本身）、
   授权来源（Luca 2026-09-20 当面批准）、旧哈希 `e0048cebe258` → 新哈希、证据目录路径。
9. 从 `docs/plan/queue/_golden_known_red.txt` 删掉 `g19b-2_stitch_crossfade` 那一段
   （连同它上面的注释）。**`g16_parallel_fx` 那一段留着。**
10. 顺手补一条测试 `test_q57_g19b2_has_no_black_frames`：跑这一例，
    逐帧断言最小亮度不为 0、alpha 全 255。这样**即使将来有人重录，也不可能把发黑重新录回去**。
    这一条比哈希更有价值 —— 哈希只说「和那天一样」，它说「没有发黑」。
