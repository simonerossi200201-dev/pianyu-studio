## 为什么这条基线是错的

g16 **并行**渲染三个工程，再和它们各自的**串行**基线比。它存在的意义就是守「并行 == 串行」
（表里那一行 `parallel==serial workers=3 vs 1`）。

- `expected_00` = `e92bb37279c9` = g11 的基线 → PASS
- `expected_01` = `1b47c4d43e9c` = g12 的基线 → PASS
- `expected_02` 现在 got = `237c6e00f384` = **g13 自己的基线，逐字节相同**；而录的是 `8eb46a915c9e`

Q47 已经 bisect 过（`docs/plan/reports/Q47_g16_bisect.md`）：`ac520ed` 时是 `8eb46a915c9e`，
`3400c86`（Q30 空间音频 / 导出混响）起变成 `237c6e00f384`。画面与 g13 逐帧差 0；
差在**音频**：旧版并行路径的 PCM 与串行相关系数只有 0.988、97.7% 采样不同。

**Q30 修好了音频一致性，并行才终于等于串行。旧基线守住的恰恰是那个不一致。**
这是这个项目第三次遇到「基线录的是缺陷本身」（前两次：9-19 的解码器、9-20 的 g19b-2）。
