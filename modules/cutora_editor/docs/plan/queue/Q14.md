## 透明素材的四个真坑（Claude 2026-09-18 补，Luca 特别强调「必须完美支持」）

Luca 的原话：「必须要完美的支持带有透明格式的 Gif 文件 和 带有透明格式的
达芬奇软件导出的 mov 格式的大文件」。仓库里已经有一部分底子，但**这四条都没解决**：

### 1. 达芬奇的透明 MOV 不是「未压缩 ARGB」
`readers._RawARGBMOVReader`（:90）只认 FourCC `0x20000000`（未压缩 ARGB 8-bit）。
达芬奇导的带 alpha 通常是 **ProRes 4444 / 4444 XQ**，像素格式 `yuva444p10le` —— 那个读取器认不出来。
而 `cv2.VideoCapture` **一律丢掉 alpha**（只给 BGR）。
所以这条链必须走 `_FFmpegFrameReader`，且 `-pix_fmt bgra`（:331/:346 已有这个分支，
**确认它对 ProRes 4444 真的被选中**，不要假设）。
先写一个探测表进 `.ok`：ProRes 4444 / 4444XQ / VP9-alpha(webm) / PNG 序列 / 未压缩 ARGB，
各自实际走了哪一层、alpha 有没有到手。

### 2. 直通 alpha vs 预乘 alpha（不处理就是黑边）
ProRes 4444 是**直通（straight）alpha**；Qt 的 `Format_ARGB32_Premultiplied` 是**预乘**。
直接塞进去合成，半透明边缘会出现**深色晕圈** —— 这是透明素材最典型的翻车现场。
读到 BGRA 后必须显式做一次 `rgb *= a` 转成预乘，或者用 `Format_ARGB32` 再由 Qt 转换。
门禁里必须有一条**边缘颜色**断言，不是只断言「alpha 不全是 255」。

### 3. 透明 GIF 的处理模式（disposal method）
GIF 是调色板 + 1 bit 透明，还有三种 disposal（不处理 / 恢复背景 / 恢复上一帧）。
按帧独立解码会出现**残影或黑底**。`cutora/media/animated.py` 已有 GIF/WebP/APNG 的入口，
**确认它是否正确处理 disposal**；不正确就修，并且用一张三种 disposal 都用到的测试 GIF 锁住。
WebP / APNG 同理。

### 4. 大文件的性能与内存（这条会撞上导出稳定态）
达芬奇的 ProRes 4444 动辄每分钟几百 MB，而 `PROTECTED_INVARIANTS.md` 第 1 条规定
**导出一律软件解码**（硬解会重置显卡驱动）。ProRes 4444 软解不便宜。
- 必须量：一条 10 秒 1080×1920 ProRes 4444 素材，叠在时间线上导出，ms/帧涨多少。
- 解码器走 Q/BUG-42 的 `_ExportCapPool`（最多同时 4 路、播完即放）—— **不许为这个素材开后门**。
- 超过「每帧 +8ms」就要做**代理**：首次导入时后台转一份 VP9-alpha 或 PNG 序列代理，
  预览用代理、导出用原件；代理生成失败不许阻塞导入，落一条状态栏提示。
- 内存：一帧 1080×1920 BGRA = 8.3 MB，缓存策略照 `_ExportCapPool` 的上限来，不许无限缓存。
