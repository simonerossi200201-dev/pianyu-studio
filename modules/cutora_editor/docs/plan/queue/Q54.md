# Q54 · 打开最近项目又慢又卡

**开工前先读 `docs/plan/queue/_RULES_FOR_EVERY_TASK.md`。**

## 用户原话

> 打开最近项目的时候挺慢而且还挺卡，这个地方是否有可以优化速度提升效率的地方呢？

## 第一步：先量，不许猜

**这一条任务的前半段是测量，不是改代码。** 这个项目已经在「量到的数字先问量的是谁」上
栽过一次（BUG-41 量的是 venv 启动壳）。

写 `tools/_diag/profile_open.py`：
- 用 `cProfile` + `time.perf_counter` 打点，跑一次真实的「打开最近项目」全流程
  （`command_project_open` → `project_io` 反序列化 → 建时间线控件 → 首帧预览 → 缩略图）
- 分段报告：**磁盘读 / JSON 解析 / 模型构建 / QWidget 构建 / 首帧渲染 / 缩略图 / 媒体探测**
  各占多少毫秒
- 用 Luca 真实的工程测（`D:\0_Dev\CUTORA` 里的 golden fixture 不够代表性，
  找一个片段数多的真工程；找不到就用 `tools/` 造一个 30+ 片段的）
- 报告写 `docs/plan/reports/Q54_open_profile.md`，**先有这份报告，再动代码**

## 已知的可疑点（当线索，不当结论）

- `main_window.py:10696` 打开工程时会跑 `migrate_open_project`，
  它会遍历所有 text overlay 做键迁移（`text_layer.py:139-160` pop 26 个扁键）
- `ffprobe` 探测：每个 clip 一次同步 `subprocess` 就够慢了。
  `media/animated.py:65-88 classify_animated` 走 `_nb_frames` ffprobe；
  查清楚打开工程时对每个媒体调了几次 ffprobe、有没有缓存
  （`animated.py:165-174` 有个带 `file_fingerprint` 的缓存，但覆盖到哪些路径？）
- 缩略图：`batch_preview.py` 的 `peek_clip_thumb` / `request_clip_thumb` 是异步的，
  但时间线上的片段缩略图是不是同步生成的？
- `stylepack.py:842 ensure_pack_thumb` 会按 `pack_content_hash` 重渲 14 个包的缩略图
  —— 这是不是在打开工程的主线程上跑的？
- QWidget 构建：几十个片段控件一次性 `new` 出来，有没有可能虚拟化（只建可视区内的）

## 「卡」和「慢」是两件事

- **慢** = 总时长长。优化方向：缓存、并行、延迟。
- **卡** = 主线程被阻塞、界面不响应。优化方向：把阻塞的活挪出主线程，
  或者至少给进度反馈（现在打开时有没有任何进度提示？没有的话，
  **哪怕不提速，加一个进度条也能把「卡」变成「在动」**）。

报告里要把这两件分开量：总时长，以及**主线程单次最长阻塞**。

## 要做的

按报告里量出来的热点排序去做，**不要一上来就全面重构**。
每改一处，重新跑 `profile_open.py` 给出前后对比数字。

如果测下来最大头是 ffprobe：做一个按 `(路径, mtime, size)` 为 key 的持久化探测缓存，
存在用户配置目录下，跨会话有效。

如果最大头是 QWidget 构建：时间线片段控件虚拟化。

如果最大头是首帧渲染：让窗口先出来、时间线先可见，首帧异步补上。

## 验收

- `docs/plan/reports/Q54_open_profile.md`：改之前和改之后各一份分段数字，同一个工程同一台机器。
- `test_q54_open_no_main_thread_block`：打开一个 30+ 片段的工程，
  断言主线程单次阻塞不超过阈值（建议 200ms）。现在大概率会红——**先让它红，再修到绿**。
- `test_q54_ffprobe_called_once_per_file`：同一个媒体文件在一次打开流程里
  最多被 ffprobe 一次（用 monkeypatch 计数）。
- 目标数字写进 `.ok`：打开时间从 X 降到 Y，主线程最长阻塞从 A 降到 B。
- golden 与 UI 基线必须不变（这是性能任务，不该改渲染结果）。
