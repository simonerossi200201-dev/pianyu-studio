## 0. 先说一件与你个人安全有关的事

**VideoKit 运行期间，你在浏览器里打开的任何一个网页，都可以读走你的 API Key，并读取你电脑上任何一个它进得去的文件。**

这不是理论推演，是三行代码叠出来的：

1. `backend/server.py:50` — `CORS(app, resources={r"/api/*": {"origins": "*"}}, supports_credentials=True)`：跨域完全放开，且允许带凭证。浏览器里的任意网页都能请求它并**读到返回内容**。
2. 后端固定监听 `127.0.0.1:5001`，**44 条路由没有任何鉴权**——没有 token、没有 Origin 校验、没有 Host 校验。
3. 于是：
   - `GET /api/settings/gladia-keys`、`/api/settings/gemini-keys`、`/api/settings/elevenlabs/keys` 直接以明文 JSON 返回你的密钥；
   - `GET /api/file/download?path=<任意绝对路径>` 没有做任何路径校验（`server.py:192`），能读走磁盘上任何可读文件；
   - `POST /api/open-folder` 会拿攻击者给的路径去执行 `explorer` / `open` / `xdg-open`。

另外 `waitress` 起服务时开了 `expose_tracebacks=True`（生产环境泄露堆栈与绝对路径），密钥以明文 JSON 落盘（`gladia_keys.json` / `gemini_keys.json` / `elevenlabs_settings.json`），`electron/main.js:1142` 还有一个 `nodeIntegration: true, contextIsolation: false, webSecurity: false` 的窗口。

**建议：需要用它时再开，用完关掉；不要在它开着的时候随便逛网页；里面填的 Key 用额度受限的小号。** 这不是黑它——是个很常见的疏忽——但对你有实际影响，所以放在最前面。

## 1. 它是什么

Electron（前端 5 MB 手写 JS，无框架）+ Python Flask/Waitress 后端 + 打包的 FFmpeg + vendored wav2lip。云端 AI 为主：**Gladia** 做语音识别与字幕对齐，**ElevenLabs** 做 TTS 与音效，**Gemini** 做文本处理。自带 80 多个 Google 字体（都带 OFL），GitHub Actions 三平台构建，electron-updater 自动更新。

八个顶层页面：一键配音字幕 / ElevenLabs / 字幕对齐 / 媒体转换 / SRT 工具 / 视频下载 / 批量 Reels / 设置。真正的"编辑器"只有**批量 Reels** 一个页面，其余是工具集合。

**它和我们最像的地方**：批量 Reels（字幕样式 + 覆层 + 水印 + 背景池 + 配乐池 + 批量渲染）几乎就是我们的目标形态；「文案自动剪辑」就是我们的智能拼接。

## 2. 它的短板（我们要避开的）

### 2.1 安全（见第 0 节）
不重复。要记住的是：**本地 API 一旦不设防，等于把用户的整台电脑挂到网上。** 我们 T13b 的做法（token 存 Windows 凭据管理器、Bearer 鉴权、Host 头非法 421、带 Origin 一律 403、从不发 CORS 头、限速、默认关闭、用户手动开启）正是这个反面教材的对照组，**任何时候都不要为了"调试方便"松开其中任何一条**。

它还给我们提了一个我们没做的醒：**API 传进来的路径必须白名单化。** 我们的命令总线也接受路径参数（`media.import`、`export.run` 的 `out_dir`、`batch.stitch` 的 folder），现在只要有 token 就能传任意路径。应当限制在"用户在设置里授权过的目录 + 当前工程目录 + 输出目录"内，越界返回错误。这条我建议加进 T13d。

### 2.2 零测试
`package.json` 写着 `"test": "node --test tests/*.test.js"`，但**仓库里根本没有 `tests/` 目录**。5 MB 的 JS、176 KB 的 Python，一个自动化测试都没有，唯一的关口是 `scripts/pre-build-check.js`。

这正是我们最大的结构性优势：golden 逐字节对拍 + 现在 172 个测试。你可能觉得这几轮"先写会失败的测试再改"很啰嗦——它换来的是我们敢动代码，而他们不敢。

### 2.3 巨文件，比我们拆之前还夸张
`src/app.js` 1.5 MB、`reels-batch-table.js` 984 KB、`batch-reels.js` 724 KB、`index.html` 518 KB、`reels-overlay-panel.js` 380 KB、`electron/services/autoEdit.js` 203 KB。我们 T01 花了大力气逃离 29,587 行的单文件，他们的 `app.js` 一个文件就是那个的好几倍，而且**没有测试兜底**，意味着实际上已经改不动了——只能往上加，不能重构。

### 2.4 核心能力绑死云端
语音识别与对齐**必须有 Gladia 的 Key**（付费、上传音频到云端），配音必须有 ElevenLabs。后果是：素材离开用户的电脑；按分钟计费；断网不能用；没有 Key 整个软件的一半是死的；供应商涨价或改 API，功能就没了。

**这是我们最硬的护城河**：whisperX 跑在用户自己的 5060 Ti 上，免费、离线、隐私、三个半小时的讲道也不产生一分钱账单。我们的 AI 提供商是**可选增强**，不是命门。这一点应该写进产品的对外介绍第一句。

### 2.5 版权与分发风险（正撞在你的红线上）
- `vendor/wav2lip/` — Wav2Lip 的官方发布（尤其是预训练权重）是**仅限非商业研究用途**的。放进一个对外分发的桌面软件里，是许可证问题。
- `assets/` 里躺着 `Hailuo.png`、`Veo.png`、`HeyGen.png`、`vidu.png`、`Dream.png`、`colossyan.png` —— **第三方公司的商标 logo**，被做成了水印预设（`config.py` 里的模式名字就叫「添加 Dream+Hailuo Logo」）。
- 打包 yt-dlp 做视频下载：工具本身许可证没问题，但功能本身邀请用户违反平台条款，他们只用帮助文档里一句免责声明覆盖。

你定的规矩是「字体绝对无版权可商用」「不涉及侵犯版权，非常友好便于分发」。这就是不守这条线的样子：**做得再好也不能卖、上不了任何应用商店、一封投诉信就能让它下架。** 我们坚持 OFL 字体 + 自有品牌 + 权限明确的模型，短期看是束手束脚，长期是能不能变成产品的分水岭。

### 2.6 它是工具箱，不是产品
八个顶层页面里塞着重命名文件、图片聚类、下载视频、转 DNxHR、调 SRT 时间……对作者本人极其顺手，对别人是一堵墙。**没有一根主心骨**——没有一个所有功能共享的工程模型，所以帮助文档不得不逐个解释四十多套流程。

我们的主心骨是**时间线 + 命令总线**：每个功能注册成命令，因此天然可批量、可配方、可被机器人调用。但这也是给我们的警告：**你后面想要的素材库、场景检测、批量工具，必须挂到这根主心骨上，而不是变成第九个标签页。**

### 2.7 破坏性操作没有撤销
它的帮助文档原话：「软件不会保证对原名提供撤销记录」。批量重命名、替换原音频、关闭复制模式直接改原素材。我们有 HistoryManager 和命令的 `undoable` / `dangerous` 标记，方向是对的——要继续保持"危险操作必须二次确认 + 留一份操作清单"。

## 3. 它做对的（值得我们拿来用的）

我不想只挑毛病。下面这几条是它真正比我们想得周到的地方。

### 3.1 预览即导出（这一条我先前说错了，改正）
我原本以为我们是"Qt 预览 + FrameRenderer 导出"两条路径，看了代码发现**我们的预览本来就直接调用 `FrameRenderer.draw_layers`**（`cutora/ui/canvas.py:732`），和导出是同一套合成代码。所以"所见即所得"我们已经有了，而且比它更硬。

**代价是性能**：每一帧都在 UI 线程上把整个字幕层从头排版重绘一遍——这正是你说的"加了字幕就卡"。这件事我单独写成了 `T14_预览播放流畅度.md`，见第 5 节。

### 3.2 文本归一化（缩小版：只留对意大利语有用的那一点）
它的 `autoEditMatcherV2.js` 用 `Intl.Segmenter` 按语言分词、NFKC 归一、按 locale 小写、编辑距离兜底。

**Luca 已明确：不面向中文和日文。** 那么按语言分词这一大块对我们是多余的——我们的目标语言（英、意、西、法、德、葡）都用空格分词，现在的 `difflib` 做法没问题，**不改**。

只保留其中很小的一点，因为它对**意大利语**是真问题：撇号与连字符的形态。文案里写 `dell'anima`（直撇号 U+0027）而 ASR 输出 `dell'anima`（弯撇号 U+2019），或者反过来，在 `difflib` 眼里是两个不同的词，直接算未命中。修法就是匹配前对两边都做 NFKC 归一 + 把各种撇号/连字符统一成一种，**大约二十行**。这不算"多语种工程"，算智能拼接的一个小 bug 修复，可以搭在 T12 里顺手做。

### 3.3 ~~FCPXML / DaVinci 导出~~ — 已否决
它能把时间线导给 Resolve / FCP 继续做。**Luca 已明确否决：片语要自己出成品，除非是高难度特效，否则全流程在片语里完成，不做达芬奇交接。**

这个决定是对的，而且比我原来的建议更有产品立场：一个软件如果要说"剩下的去 Resolve 里做"，等于承认自己没做完。记在这里只是留个档——如果将来把软件卖给别的剪辑师、而他们要求交接，再重新评估，Phase 1–3 不做。

### 3.4 素材池 + 组合规则
背景池 / 配乐池：一组素材 + 随机或组合规则，批量任务从池子里取，还能「拼接并设为背景」。这比"素材库让你浏览和拖拽"高一个层次——**它是给批量用的**。你的 T11 资产库应该长成这个样子，而不只是个素材浏览器。

### 3.5 表格粘贴进批量表
「从表格粘贴」——从 Google Sheets / Excel 复制一列文案，直接粘进批量任务表。极低摩擦。我们的批量表应该支持 TSV 粘贴，实现成本很低，对你现在的流水线立刻有用。

### 3.6 我们缺的几个媒体工具，都不难但很实用
- **场景检测**（按镜头切分 + 每场景导出帧）——它同时喂养 b-roll、封面、Shorts 候选；
- **智能关键帧**（场景检测 + 每场景额外采样 → 帧网格里挑图）——做封面的正经做法；
- **智能聚类分类**（按感知哈希把图片/视频分组）——整理素材库；
- **音频检测匹配**（把处理过/重录的音频与视频对齐后替换，支持 ±10/50 ms 微调和试听）——很实在的工程工具；
- 批量截图 / 统一命名 / 批量重命名（带预览列表）。

其中**场景检测**优先级最高，它是很多下游功能的输入。

### 3.7 发布与供应链的纪律
electron-updater + 更新通道、GitHub Actions 三平台构建、CodeQL 配置、构建产物签名声明（attestation）。它的 `.agents/AGENTS.md` 还专门记了两条血泪教训：**必须先推代码再打 tag**（否则 CI 构建的是旧代码）、**必须上传 `latest.yml`**（否则自动更新永远发现不了新版本）。这两条直接抄进我们的 T10。

### 3.8 一份写给人看的说明书
`软件使用帮助文档.md` 写得相当好：按界面组织、每个参数都解释、明确标出哪些操作会毁掉原素材、末尾有常见问题。我们的 `docs/api/` 是给机器人看的，**还欠一份给人看的**。

## 4. 全部做完之后，我们能不能完胜它

诚实的判断，分三段：

**Phase 1 结束时**——我们在"编辑质量与可信度"上全面胜出：真正的时间线与撤销、golden 回归、本地识别（免费/离线/隐私）、安全的本地 API、可换肤的界面、能被机器人操作。但我们在**工具广度**上输（他们有下载、格式转换预设、场景检测、聚类、重命名、TTS、FCPXML），**平台**上也输（他们 mac/win/linux 三平台，我们只有 Windows）。

**Phase 2–3 结束时**——我们在核心上决定性领先：转录稿驱动剪辑、去废话与静音压缩、说话人分离、Shorts 候选评分、自然语言指挥剪辑。这些东西**对一个 1.5 MB 无测试的单文件应用是架构上够不着的**——不是他们不聪明，是改不动。

**他们会一直领先的地方（除非我们动手）**：FCPXML/Resolve 交接、内置 TTS、媒体工具广度、跨平台、自动更新。

所以结论是：**方向没问题，主心骨比它强，但有五件具体的事要现在就写进计划**，否则等做完了才发现缺，补起来更贵。

### 5.1 关于"写路径白名单"到底有没有必要

先把我原来的理由划掉：我写的是"对照 VideoKit 的任意文件读取"——**那个类比不成立**。VideoKit 的问题是**完全没有鉴权**，任何网页都能调；我们的 API 要 keyring 里的 token、拒绝带 Origin 的请求、校验 Host、默认关闭。能调到我们 API 的东西，已经是"以 Luca 的身份在这台机器上运行的程序"，它想读文件根本不需要绕道我们的 API。**所以作为防黑客手段，这条几乎等于零。**

真正的理由是另一个，而且和你正在做的事直接相关：**T13 的全部意义是让 AI 代理来操作这个软件**（Grok Bot、Claude Desktop 通过 MCP）。代理会读网页、读文档、读转录稿，然后决定调哪条命令——这意味着**一段被塞进素材文案里的提示词注入，有可能让代理调出一条 `export.run` 把文件写到不该写的地方，或者一条危险命令覆盖掉别的东西**。白名单不是防人，是**给代理划一个活动范围**：出了范围就报错，而不是照做。

所以我的建议缩成这样，尽量不添麻烦：
- **只约束写入**（导出目录、另存为、批量输出），读取不限制——读取的风险前面说了，本来就挡不住，限制它只会误伤。
- **只约束 `source` 为 `api` / `mcp` / `recipe` 的调用。** `cli` 和 `ui` 不受影响——**这一条很重要**：你的 flow 流水线在 `D:\1_PROJECT` 底下到处写文件，如果白名单管到 CLI，你现在的自动化立刻会断。
- 默认允许：当前工程所在目录、设置里的默认输出目录、素材库目录、用户在设置里手动添加的目录。
- 越界时报错要说清楚"哪个路径、为什么不允许、去哪里加白名单"，不能只报一句拒绝。

如果你觉得这仍然是多此一举，**不做也完全说得过去**——目前只有你一个人用，代理也是你自己指挥的。我的意见是：等 Phase 4 真的开始让代理无人值守跑夜班时，这条会变得有意义；现在做的好处只是趁 T13 还在手上顺手，成本大约一小时。你定。

## 6. 这些改动会不会有负面影响

你让我想清楚代价，逐条说：

**T14 预览性能** —— 风险有两个。一是**改坏导出**：靠 golden 逐字节对拍挡住，任务书写明只碰预览路径，导出调用点行为一字不变。二是**预览与成品不一致**：播放时降质是必要的（Resolve 也这么做），但你必须知道自己看的是不是最终画质，所以任务书要求暂停时恢复全质量，并且新增一个"暂停态预览 = 导出帧，逐像素一致"的测试把这条锁死，画布上还有个小标记提示当前是快速预览。除此之外没有别的代价——这一条是纯赚。

**写路径白名单** —— 唯一风险就是误伤，所以限定"只管写、只管代理、不管 CLI 和界面"，并且报错要能自助解决。做不做都不影响别的功能。

**撇号归一化** —— 会改变智能拼接的匹配结果，所以必须跑 golden；g04 是真正走拼接的用例，它的文案里如果没有撇号，输出应当逐字节不变。风险极低。

**否决 FCPXML 与多语种分词** —— 纯粹是少写代码，没有负面影响。反而省下的时间可以投到 T14 和素材库上，那两样你每天都会用到。

**总的说**：这一轮调整之后，计划变短了、更聚焦了，而且新增的那条（T14）解决的是你每天都要忍受的问题。这是好的方向——竞品分析最大的价值，往往不是"抄它什么"，而是"确认哪些事根本不用做"。
