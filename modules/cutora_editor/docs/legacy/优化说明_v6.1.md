## 先看一个数字

沙箱实测：**一次串行导出总共只用到 1.82 个 CPU 核心**（Python 渲染线程 0.45 核 + FFmpeg 1.37 核）。

把这个数字放到你的机器上：

```
1.82 / 32 线程 = 5.7%
```

你任务管理器里看到的是 **6%**。

所以那个"占用超低"不是显示错误，也不是硬件没配合好——是软件**真的只在用不到 2 个核**，另外 30 个核全程闲着。风扇响是因为那 1 个满频狂飙的核。

## 一、修复：双开崩溃（显存不释放）

### 问题

`whisperx.align()` 对整段音频一次性推理时，PyTorch 的 caching allocator 会向驱动申请数 GB 显存。推理结束后这些块留在 allocator 内部**不归还驱动**。而全文件唯一一次 `torch.cuda.empty_cache()` 在对齐**开始前**（原 2937 行），结束后不调用。

结果就是你截图里那个矛盾：**专用 GPU 内存 11.0/16.0 GB，GPU 利用率 4%**。11 GB 被占着但没在算。

第二个实例启动时，要建 CUDA 上下文（~0.5GB）+ 加载自己的模型（~2GB）+ NVENC 会话，剩下 5GB 不够 → CUDA OOM → 崩溃。

### 改动

**1. 自动回收**（`AlignmentWorker.run` 末尾新增 `finally`）

```python
finally:
    trim_gpu_cache("AI字幕结束")
```

每次 AI 字幕任务结束后，把 allocator 里的空闲块还给驱动。模型保持常驻，下一个视频不需要重新加载，速度不受影响。无论成功、失败还是中途 `return`，`finally` 都会执行。

**2. 手动彻底释放**（新增「性能 → 释放显存 (卸载 AI 模型)」菜单）

卸载 ASR + 对齐模型并清空缓存。下次运行自动字幕时会自动重新加载（本来就是惰性加载），功能不受任何影响，只是那一次会多几秒模型加载时间。

**准备双开前点一下这个，是最直接的解法。**

**3. 显存查看**（新增「性能 → 显存占用情况」菜单）

显示显卡型号、总显存、模型实际占用、PyTorch 保留量、ASR 模型加载状态。

## 二、修复：RTX 50 系被误判为"不受支持"

### 问题

项目里有**两套互相矛盾**的 GPU 架构白名单：

| 位置 | 判断条件 | 你的 sm_120 |
|---|---|---|
| `config.py` 启动检测 | `60 <= cc <= 120` | ✅ 通过 |
| `AutoSub_debug.py` 的 `toggle_gpu` | `70 <= cc <= 90` | ❌ 被拒 |

启动时因为 `setChecked()` 写在 `toggled.connect()` **之前**，侥幸不触发。但你**手动点一下 GPU 勾选框**，就会弹「当前显卡架构 (sm_120) 不受支持」，然后 GPU 加速被永久关掉——而且再点也勾不上，因为每次勾选都会被这段代码打回。之后所有导出退回 `libx264` 软件编码。

**连带的隐性 bug**：`AutoSub_debug.py` 用的是 `from config import DEVICE`，这是**值拷贝**。`toggle_gpu` 里写 `config.DEVICE = "cpu"` 只改了 config 模块的属性，本模块里 `get_whisperx_model()` 和 `whisperx.align(..., DEVICE, ...)` 用的还是导入那一刻的旧值。这个开关对 AI 推理半失效、对导出编码器全生效。

### 改动

**1. 单一事实源**：`config.py` 新增 `detect_gpu_config()`，把架构判断收敛成一个函数。启动检测和 UI 开关**都调用它**，不可能再分歧。

```python
def detect_gpu_config(verbose=True):
    """返回 (device, compute_type, reason)"""
    # 60~69   Pascal        → int8
    # 70~89   Turing/Ampere/Ada → float16
    # 90      Hopper        → float16
    # 100~120 Blackwell     → float16   ← 你的 5060 Ti
```

**2. 修掉值拷贝**：新增 `_sync_device_globals()`。所有修改 `config.DEVICE` 的地方都紧接着调用它，把值同步回本模块。模型缓存本身会检查 `_WHISPERX_DEVICE == DEVICE`，设备变了会自动重新加载，切换是安全的。

**3. 勾选框初值**改为读 `config.DEVICE`，而不是裸的 `torch.cuda.is_available()`（后者在架构不受支持时仍返回 True，会显示"已启用"但实际跑在 CPU 上）。

## 三、消除开场视频的重复转码

### 问题

`_concat_intro_video()` 在主渲染**之前**，先把「开场 + 主片」用 ffmpeg 完整重编码到临时文件：

```python
"-c:v", "libx264", "-c:a", "aac",     # 没有 -preset，没有 -crf
```

不指定就是默认 `preset=medium` + `CRF=23`。然后这个临时文件又被逐帧解码、重新渲染、重新编码。

双重代价：**时间**上全片多一次 medium 转码；**画质**上 CRF 23 压一遍再按 CRF 18 压一遍，你在导出设置里调的高画质被这一步提前糟蹋了。

### 改动

优先用 NVENC 硬件编码，失败自动回退 libx264 `ultrafast`，两者都用接近无损的量化参数（CQ/CRF 12）：

```python
NVENC : -preset p1 -rc constqp -qp 12
x264  : -preset ultrafast -crf 12
```

CRF 12 远高于最终输出的 CRF 18，所以对成片画质**只赚不亏**，同时快得多。

## 四、无损模式的 preset 选反了

```python
if self.export_mode == "original":
    preset = "medium"    →  "ultrafast"
    quality_args = ["-crf", "0"]
```

CRF 0 是数学无损，`preset` 只影响「编码速度 / 文件体积」这对权衡，**对画质没有任何影响**（已经无损了）。`medium` 在这里纯粹是白白浪费 CPU。

## 五、导出期间挂起预览定时器

- `self.timer` —— 200ms，`sync_ui()`
- `self.timeline.timer` —— 100ms，`update_scroll_range()`

这两个只服务于预览显示，与导出结果无关。但整条流水线的瓶颈就是那**唯一一个** Python 渲染线程，主线程每 100ms/200ms 醒来抢一次 GIL 就是直接减速。

新增 `_suspend_preview_timers()` / `_resume_preview_timers()`，用计数器保护，支持批量导出中反复调用而不会提前恢复。

## 六、覆层判定改用二分查找

`_has_visible_overlay()` 原本每帧线性扫描全部 `segments` + `text_overlays` + `image_overlays`，复杂度 O(帧数 × 覆层数)。

新增 `build_overlay_index()`，导出前一次性构建按 start 排序的区间索引 + end 前缀最大值数组，之后每帧改用 `bisect` 二分查找。

**已用 12 万次随机对拍验证**（含 `end < start` 的畸形数据、空列表、缺失字段等边界情况），与原线性扫描判断结果**完全等价**，0 处不一致。

## 七、核心改动：多进程并行导出

### 为什么不能用多线程

渲染路径重度依赖模块级全局可变状态：

| 全局变量 | 用途 |
|---|---|
| `_SE_SUB_CACHE` / `_SE_OV_CACHE` | 字幕/覆层整体特效缓存 |
| `_IMAGE_CACHE` | 图片素材缓存 |
| `_DBI_VIDEO_CAPS` / `_DBI_VIDEO_FRAME_CACHE` | 视频解码器与帧缓存 |

两个渲染线程同时跑会互相覆盖缓存 → **画面串台**。更致命的是 `cv2.VideoCapture` 完全非线程安全（共享内部 seek 位置），两个线程同时 `.read()` 必然读到错乱的帧或直接段错误。

原代码注释里写着「稳定性：严格串行——导出未结束时绝不启动下一条」，这个决定是**对的**。

**所以只能走多进程**：每个子进程有自己独立的全局缓存和解码器，天然隔离。

### 实现

**子进程入口**：`python AutoSub_debug.py --render-job <job.json>`

关键设计：

1. **渲染逻辑零分叉**。子进程复用**完全相同**的 `RenderWorker`，只是不调用 `.start()` 而是直接 `.run()` 同步执行。所以并行产物与串行产物必然一致（已验证逐字节相同）。

2. **子进程不加载 torch / transformers**。通过 `AUTOSUB_RENDER_CHILD=1` 环境变量：
   - `torch` / `whisperx` 改为 `_LazyModule` 惰性代理，第一次访问属性时才 import
   - `config.py` 跳过 CUDA 检测
   - 跳过启动依赖自检（`transformers` 光 import 就要 3~5 秒）

   实测子进程**导入耗时 0.20 秒**，全程不建 CUDA 上下文。如果不做这层，6 个子进程光上下文就能吃掉 6GB 显存，把 16GB 的卡挤爆。

3. **一个进程包干一批，不是一个视频一个进程**。这一条是实测之后改的：进程启动固定开销约 0.5~1 秒（PyQt 导入 + 注册 232 个内嵌字体）。最初按「一视频一进程」实现，实测 6 个 4 秒视频反而**比串行慢**（0.78x），启动开销把收益全吃了。改成轮询分批后，这笔开销总共只付「进程数」次。

4. **进度用临时文件传递，不用管道**。管道要求父进程持续读取，读慢了会把子进程卡死。用 `os.replace()` 原子写入，父进程绝不会读到半个文件。

5. **失败绝不丢视频**：
   - 单个视频失败 → 记录后继续做下一个，最后写进 result 文件
   - 整个子进程崩溃 → 读不到 result 文件，父进程把它负责的**全部**退回串行重试
   - 并行启动失败 → 直接落回原串行逻辑

   最坏情况只是退化成原来的速度。

### 使用

「性能」菜单新增：

- **并行批量导出**（开关，默认关闭）
- **并行进程数**（默认 = 核数 / 4，夹在 2~6，你的机器是 6）

上限 6 是为了给 NVENC 留余量（消费级 RTX 驱动允许 8 路并发编码），同时避免磁盘 I/O 成为新瓶颈。

### 预期收益

按实测的「每次导出 1.82 核」推算：

| 并行进程数 | 预计 CPU 占用 | 相对现状 |
|---|---|---|
| 1（现状） | 5.7% | 1x |
| 2 | 11% | ~2x |
| 4 | 23% | ~4x |
| 6 | 34% | ~6x |

**注意**：这是按 CPU 余量推算的上限。实际会被磁盘写入、NVENC 并发数、以及视频本身的复杂度拉低。建议从 4 开始试，观察任务管理器占用再往上加。

## 没有做的事

报告里提过但**刻意没做**的一项：

**静态图层帧级缓存**（文字/图片覆层在显示区间内若无动画，只渲染一次后复用 QImage）。

理由：这需要判断每个覆层在当前帧是否"真的静止"，而 `draw_layers` 里有打字机、逐词高亮、呼吸、抖动等十几种动画路径，任何一处判断失误都会导致动画卡住或丢帧。收益中等，但破坏功能的风险明显高于前面所有改动。

如果你之后确认并行导出已经够用，这一项可以不做；如果还想继续压榨单个视频的速度，我们可以针对具体的动画类型逐个验证后再上。
